# The KillerBench.Engine capability catalog

This is the detailed implementation catalog for the current Engine. Start with the [Engine README](../README.md) for the short orientation and documentation map.

## Source layout

Engine source is grouped by capability. Public types retain the `KillerBench.Engine` namespace, so moving a file between these folders does not change the API.

- Product areas: `Applications`, `Audio`, `Backup`, `BitLocker`, `Cleanup`, `Crash`, `Debloat`, `Devices`, `FileSystem`, `Installation`, `Network`, `Printing`, `Profiles`, `Scheduling`, `Security`, `Services`, `Storage`, `System`, `Time`, and `Updates`.

`DefaultAudioEndpoints` provides bounded role-specific Core Audio evidence for embedders. It reports endpoint identity, state, form factor, shared format, master volume, mute state, shared-mode effects, event-driven support and whether the endpoint accepts its current shared mix format for an exclusive-mode request. `AudioExclusiveMixFormatStatus` keeps accepted format, unsupported format and endpoint-policy refusal distinct. These results do not open an audio stream or prove application permission, playback, recording, per-channel levels, live signal activity or routing.

`AudioOperationalCorrelation.Check` combines the selected audio device and driver results, role-specific default endpoint results and exact Audio Endpoint Builder and Windows Audio service histories into one conservative workflow outcome. Missing, duplicated, excessive or unexpectedly named groups fail closed. Incomplete evidence takes precedence over current or historical attention. A complete result without findings remains informational because KillerBench does not open an audio stream or prove playback, recording, application permissions, routing, live signal, Bluetooth transport or physical device operation. The focused Audio workflow and its CLI workflow entry expose the result. It never selects a repair or changes an endpoint, device, driver, service, format, effect, volume, mute, policy or audio setting.

`ThirdPartyUpdatePlanning` and `ThirdPartyUpdateExecution` expose an exact-package application update boundary for the desktop, CLI and embedders. A selection contains the package ID, source and target version returned by complete `Microsoft.WinGet.Client` discovery. Execution requires explicit agreement acceptance, repeats discovery after durable preparation, invokes WinGet for one exact ID, source and version in silent noninteractive mode, omits broad, force, security-bypass and automatic-reboot switches, then verifies the exact installed version through fresh typed inventory. Uncertain dispatched operations retain a same-machine pending record and block retries. `ReconcileAsync` can archive that record only after exact installed-version evidence and never invokes WinGet upgrade. Native installation remains disposable-machine validation work.
- Shared analysis: `Evidence` and `Knowledge`.
- Coordination: `Workflows` and `Automation`.
- Common process, persistence, and recovery helpers: `Infrastructure`.

`NativeValidationCatalog` provides one deterministic disposable-VM plan for every installed recipe. Each plan preserves the recipe ID, version, area, action, execution mode and recovery contract, then assigns stable scenario IDs for healthy evidence, incomplete evidence, provider failure and cancellation. Executable recipes also require rejected eligibility, preview, verified execution, verification failure, interruption after dispatch and read-only reconciliation. Option-driven, policy-aware and restart-capable actions receive their additional required cases. `validation-plan` exports all plans or filters them by exact recipe ID or workflow without collecting machine evidence or executing a repair. The catalog defines required validation; it never claims that native validation has occurred.

`NativeValidationEvidence` accepts bounded schema-1 disposable-VM records only when the recipe version and scenario ID match the installed catalog. Records identify the Windows product, version, build and architecture plus the KillerBench version and UTC observation time. Every scenario-required artifact must have a unique kind, filename-only label and exact SHA-256 digest. Coverage selects the newest valid record for each scenario and keeps Passed, Failed, Blocked, Inconclusive and missing counts separate. `validation-record` validates one file and `validation-coverage` summarizes up to 4,096 files. Neither command reads artifact contents, runs diagnostics, executes repairs or turns a recorded pass into a broader repair claim.

`PreviousWindowsInstallationRemoval` coordinates the option-dependent `windows.previous-installation-removal` cleanup recipe. Preview and review are read-only. Execution requires the exact local `Windows.old` directory on the Windows volume, rejects reparse points, confirms that Windows reports OS rollback as available, and requires administrator access, clear restart evidence, idle servicing, explicit execution and backup confirmation. Verification requires Windows to report that rollback is no longer available. KillerBench does not recursively delete `Windows.old`, restart Windows or claim immediate space reclamation. A dispatched uncertain result retains its pending guard. `ReconcileAsync` reads current state without repeating DISM and distinguishes Verified, NotChanged and Inconclusive outcomes. The desktop exposes this as a separate Cleanup action. CLI access is preview-first through `previous-windows`, requires both `--execute` and `--backup-confirmed` for mutation, and provides `previous-windows-recover` for no-repeat reconciliation. Native execution remains disposable-VM validation work.

### Windows Memory Diagnostic results

`MemoryDiagnosticResults.CheckAsync` reads only `Microsoft-Windows-MemoryDiagnostics-Results` records from the System log for the last 14 days, retaining at most 200 records with a 20-second command bound. Vitals, Full system scan and `vitals-check` include the result, while `memory-diagnostic-results` exposes it directly. Warning, error and critical levels request review; informational records remain history. Exact event payload is retained because result fields vary across Windows versions, but KillerBench does not translate localized text into a pass or failure claim. Empty history does not prove that a test ran. A historical pass does not establish current memory health, and warning or error history does not identify a replaceable module. No test is scheduled or run and no repair is selected. A native read-only run returned complete empty history and requested no test or system change; nonempty and adverse native histories remain disposable-VM work.

### Structural minidump analysis

`MinidumpAnalyzer` validates the Microsoft minidump signature, a maximum of 128 stream-directory entries and bounded system-information, exception and module-list structures. It reports only the dump filename, processor architecture, Windows version, exception code and basename of the one module whose declared image range contains the exception address. RVA ranges, duplicate stream types, module counts and UTF-16 name lengths are checked before reading. Crash review analyzes at most the three newest discovered dump candidates, and `minidump-analyze PATH` exposes one exact file through the CLI. Full kernel, active-memory and other dump formats are reported as unsupported instead of guessed. Memory pages, registers, thread contexts, stack frames, symbols, command lines and full module paths are not read or retained. Structural identity does not establish root cause or authorize repair. Fixture coverage includes valid, unsupported, truncated, excessive, duplicate, out-of-range and canceled input. Native Microsoft minidumps, access failures and non-x64 architectures remain disposable-VM validation work.
