# Native validation queue

Pending as of September 14, 2026. No native repair pass is claimed below.

## Automated fault injection for pack recipes

`killerbench-cli validate-native RECIPE_ID SCENARIO_SUFFIX|all OUTPUT_DIR --disposable MACHINE_NAME` injects the fault for each catalog scenario of a service-pack recipe (stop the service for eligible preview, verified execution and cancellation; stop and disable it for rejected prerequisite; observe only for healthy), runs the pack recipe through the shared runner, restores the injected state, and writes one validation record per scenario with its artifacts. Scenario kinds the runner cannot inject natively are recorded as Blocked with the reason, so the report stays honest. It refuses to run unless `MACHINE_NAME` is this machine and `KILLERBENCH_DISPOSABLE` equals `yes-this-machine-is-disposable`; never set that on a development or customer machine. `Tools/Validation/Invoke-NativeServiceValidation.ps1` loops every service recipe and builds the HTML report. As of September 18, 2026 no native pass has been run; the runner itself is covered by fixtures only.

The source catalog contains 101 workflows and 115 recipes, including diagnostic-only entries. Full system scan exposes 96 selectable recipes, including every installed exact-service recovery recipe except the focused Windows Update Medic demand-start boundary. Focused workflows expose Windows Update Service, Windows Update Medic, Update Orchestrator and Delivery Optimization recovery, structural Windows Update data-store recovery, exact BITS job retry, explicit Windows Time source configuration, exact diagnostic event-channel enablement, exact standalone computer rename, exact BitLocker recovery backup, guarded Outlook cache retention, previous Windows rollback removal, High performance power-plan activation, selected power-timer changes and hibernation disablement only when their bounded evidence collection and target selection are deliberately requested. Counts describe organization, not reliably repaired faults. Background checks use substituted providers, parser fixtures, journals and harmless child processes. Read-only development-machine observations do not validate repairs. The complete 96-recipe combined path still needs disposable-VM coverage, including automatic stopped core infrastructure services and the later service additions, before broad repair claims are supportable.

Windows Update Medic validation must cover running, stopped enabled demand-start, disabled, missing, protected, access-denied, transitioning and incomplete states. Combine each state with present, missing, non-Valid and unavailable registered DLL evidence; idle, active, failed and incomplete bounded Windows Update activity; and empty, matching and incomplete exact failure history. Confirm incomplete evidence takes precedence and that DLL observations, activity and history never authorize a start or component action. Confirm that only the focused workflow can authorize a start and that policy, source enrollment, schedules, packages, BITS jobs, restart settings, permissions and startup type remain unchanged. Record resumed remediation or update activity separately from stable service-state verification.

Focused Delivery Optimization validation must combine running, stopped, paused, transitioning and unavailable exact service states with empty, active, paused, mixed and incomplete activity snapshots; classic-only, Policy CSP-only, mixed, empty and incomplete policy evidence; and empty, matching, unrelated, capped and unavailable exact failure history. Confirm incomplete evidence takes precedence, service, policy and historical concerns remain review-only in the combined conclusion, historical failures never authorize continuation, and only the separate exact Paused current-state recipe can authorize one continuation request after administrator, restart and final-state checks. Verify the conclusion never claims transfer progress, cache health, peer reachability, applicability or completion.

`killerbench-cli validation-plan` exports the installed recipe catalog as deterministic JSON with stable scenario IDs and required evidence artifacts. Filter it with `--recipe RECIPE_ID` or `--workflow WORKFLOW`. The output covers universal healthy, incomplete, provider-failure and cancellation cases plus preview, eligibility, option, managed-authority, execution, verification, interruption, restart and no-repeat reconciliation cases where they apply. It is a test plan only. It does not run diagnostics or repairs and does not prove that a native scenario passed.

Store one JSON record per executed scenario and validate it with `killerbench-cli validation-record RECORD.json`. Each record must match the installed recipe version and stable scenario ID, identify the Windows and KillerBench builds, and include every required artifact by kind with a filename-only label and SHA-256 digest. `killerbench-cli validation-coverage RECORD.json [...]` keeps the newest record per scenario and reports passed, failed, blocked, inconclusive and missing totals. Old recipe versions, unknown scenarios, future timestamps, path-bearing artifact names, missing artifacts and invalid hashes are rejected. These commands only read evidence files and never run a diagnostic or repair.

Use `killerbench-cli validation-report OUTPUT.html RECORD.json [...]` for a searchable coverage matrix or choose `.txt` for a portable text report. The HTML report includes all 13 Killer Tools themes, status filtering and every installed scenario. It keeps missing evidence separate from Passed, Failed, Blocked and Inconclusive records. Report generation reads validated records only and performs no machine inspection or repair.

## Test layers

Use deterministic Engine fixtures for individual states, generated pairwise cases for interactions, disposable VMs for Windows integration and physical machines only for hardware behavior that virtualization cannot represent. Demo mode is for interface and presentation review. It is not repair validation.

The minimum VM pool is Windows 10 and Windows 11, each with clean and policy-managed snapshots. Add reusable fault snapshots for pending restart, servicing corruption, stopped or disabled services, failed Windows Update, printing failure, network failure, low disk space and BitLocker protection changes. Domain-joined testing can reuse the policy-managed machines on an isolated test domain. Restore the baseline after every mutating case.

Do not build one VM for every combination. Generate pairwise cases across OS build, elevation, policy ownership, restart state, service state, provider completeness, disk capacity and repair outcome. Promote a combination to a VM scenario when it depends on real Windows side effects, reveals a fixture mismatch or covers a recovery contract that has not received native validation.
