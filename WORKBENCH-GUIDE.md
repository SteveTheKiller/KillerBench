# KillerBench usage and technical reference

For embedding, framework targets and platform-provider boundaries, see the [Engine README](Engine/README.md). Database generator organization is documented in [Tools/Knowledge](Tools/Knowledge/README.md). The standalone builder includes an IEEE MAC-assignment CSV importer, and the Engine and CLI provide longest-prefix lookup against a generated local pack. Other production importers and signed publication remain unfinished.

Windows maintenance workbench, version 0.1.0 in development. KillerBench combines diagnostics, guarded repair, cleanup, update review, maintenance and security tools in one local app. Diagnostics opens to Full system scan, which runs all 49 diagnostic areas and checks all 96 guarded repair recipes. Correlated areas end with a clear readiness verdict while preserving their detailed evidence. Automatic repair remains off until selected. After GO, the readable report puts the recommended next step and anything needing attention ahead of collected information, while Raw output retains the detailed evidence for review and export. The CLI equivalent is `full-scan`; the named Engine entry point is `FullSystemScan.RunAsync`. Cleanup supports optional permanent removal; update installation requires explicit selections. Maintenance also includes a Browser extensions workflow that reports bounded Chrome, Edge, Brave and Firefox extension identities through the normal GO, report, journal and export path. Installed applications can compare two saved inventories or review one exact application folder name at five fixed roots, and Storage can review duplicate or large files in one selected folder. These reviews produce readable reports, retain detailed raw evidence and never delete files or applications. SHADE privacy inspection remains read-only except for separate guarded Clipboard history and the 18 account-setting controls in the Privacy setting selector. BERET BitLocker supports guarded recovery-file backup, protection resume and a constrained encryption path. See [native tool coverage](SCRIPT-CAPABILITIES.md) for implemented and unfinished script capabilities.

The advanced diagnostic-only selector initially shows 11 outcome groups covering servicing, network, storage, printing, installation, services, Windows Update, backup, system stability, security and application deployment. Application deployment includes registered and provisioned packaged-app state plus bounded machine and current-account Win32 registration summaries. Select **Show individual evidence areas** only when a focused investigation needs one of the 49 underlying collectors. Diagnostic-only selection always excludes recipe checks and repairs.

**MACE** reviews explicit OneDrive, Outlook, Office/Microsoft 365, Project and Teams selections across exact application, package and Click-to-Run registrations. Account scope, application-data retention, cached-credential retention and OneDrive folder-location review are explicit choices. Bounded safeguards review selected app processes, OneDrive known-folder containment, product-level credential references, fixed application-data locations and fixed machine or current-account policy areas. They exclude process identities, paths, filenames, contents, policy names or values, usernames, attributes and secrets. Shared Office and Project locations and policy remain labeled as shared. Exact provider classification identifies the current-account loose-file development package boundary and records explicit unsupported reasons for ordinary installed packages, classic uninstall registrations, provisioned packages, Click-to-Run products and protected packages. After GO, the desktop lists supported package candidates in one selector and shows the selected package plan in the main evidence display. GO is review-only. The separate red desktop control requires an eligible review, an unchecked consent selection and a second confirmation, then repeats all eligibility evidence, records durable preparation, sends one exact current-account package request, verifies absence and never repeats an interrupted request. Check interrupted removal uses fresh inventory to resolve a prior durable record and never repeats removal. CLI: `mace-review --all-products --json`, `mace-package-plan --outlook --package PACKAGE_FULL_NAME --json`, or `mace-package-recover`.

Backup readiness and **Backup services** read the local WindowsServerBackup provider summary when that optional provider is installed. The result includes only the last backup time, last successful time, next scheduled time and numeric last result. Targets, credentials, item lists and provider messages are excluded. A nonzero last result requests review but does not identify a cause or authorize a service start. Missing provider support is informational because it says nothing about third-party backup products or File History. CLI: `backup-summary`.

The same views inventory bounded VSS provider registrations by name, version and documented type. Provider IDs and COM class IDs stay out of ordinary results. Missing system-provider or unknown-type evidence requests review, but registration never proves that a snapshot, backup or restore can complete. CLI: `vss-providers`.

They also summarize current shadow copies by creation range, documented state and privacy-safe attribute counts. Aborted or adverse-status records request review. Transitional records remain informational until correlated with later observations and VSS events. Snapshot, provider, volume, device, machine and path identities are excluded. CLI: `shadow-copies`.

The same backup views read the current account's File History protection state through the deprecated Windows configuration interface. The protected-until timestamp, target identity, configuration paths, protected items and credentials are excluded. The state is a bounded Windows observation, not proof that destination contents are current or restorable. Unknown future values and incomplete provider results remain incomplete, and no state authorizes a backup or repair. CLI: `file-history-status`.

The same backup views read up to 200 warning, error and critical records from the File History backup log during the last 7 days. Only severity counts plus the newest event ID, level and time are retained. Messages, event payloads, configuration paths, accounts, computer names and destinations are excluded. More than 200 records, malformed output or failed collection remains incomplete. An empty event window does not prove File History is configured, current or recoverable, and historical records never select a repair. CLI: `file-history-events`.

Vitals and Full system scan review the three newest discovered crash-dump candidates with a bounded structural minidump reader. It can show an exception code and containing module basename when those exact structures are valid. It does not read memory pages, stacks, registers, symbols, command lines or full module paths. Full kernel and other dump formats remain explicit unsupported evidence. Use `minidump-analyze PATH` for one exact local file. Structural metadata is an investigation lead and never selects a repair.

Crash review also groups the retained System Error Reporting records into incidents. An incident links to dump metadata and structural analysis only when the event reports the exact collected path. KillerBench does not use timestamp proximity or a matching filename to guess ownership. Duplicate event identities, ambiguous paths and incomplete inputs remain incomplete. The summary shows a dump basename, code and available structural result; retained evidence preserves the exact source association. A path can be reused or overwritten, and a containing module is not proof that its driver caused the crash. Use `crash-review` for the same Engine flow through the CLI.

The CLI command `diagnostic-scopes` returns those 11 recommended groups as JSON. Add `--all` to return all 49 individual and aggregate areas. This command performs no collection.

Service readiness checks registered service executable, driver and ServiceDll presence on fixed local volumes while excluding full paths, arguments, accounts, process IDs and signer identities. Present local executables, drivers and registered DLLs receive bounded Authenticode status checks. UNC, non-fixed and unparseable locations are not contacted. A separate quoting review identifies user-mode service executable paths that contain spaces but are not quoted. It excludes full paths and arguments and requests package-specific review without selecting a registry edit. Logon review reports only built-in, virtual, managed or named account classes plus desktop interaction, excluding account and domain identities. Ordinary account classes remain context, while an interactive service outside LocalSystem requests package review without selecting an account change. Startup configuration review counts automatic, manual, disabled, boot, system and delayed-automatic registrations from the same bounded inventory. It requests package review only for driver-only boot or system modes on an established user-mode service or a delayed-start flag outside an automatic user-mode service. Disabled and demand-start settings remain configuration context and never select a startup change. Dependency review joins direct service dependency names to the complete bounded Services registry, detects absent identities, self-dependencies and cycles among installed Win32 services, and counts load-order group use without expanding group membership. It does not infer that a dependency should be added or removed. The DLL check covers only explicit `ServiceDll` values and does not load a DLL or prove service behavior. Missing or non-Valid files request approved-package review without selecting replacement. Recovery evidence inventories action types, delays, reset periods and whether configured actions apply to non-crash failures while excluding commands and reboot messages. Trigger summaries retain types and start or stop actions without subtype IDs or payloads such as device IDs, ports, paths, named pipes or RPC interfaces. A stopped demand-start service with configured triggers can be idle while Windows waits for its event. These settings are context rather than a health verdict and do not prove that a binary can load or that recovery or a trigger action succeeded. Service readiness repeats the installed-service inventory only when the first complete snapshot contains Start Pending, Stop Pending, Continue Pending or Pause Pending. The same service remaining in the same exact transition requests review; a changed state or identity remains informational. This bounded observation does not prove a hang, select a repair, or start, stop, continue, pause, restart or reconfigure a service. Use `workflow services --json` for the combined Engine evidence, `service-startup-config` for startup-mode coherence, `service-dependencies` for direct dependency integrity, `service-binaries` for executable and driver presence and signature status, `service-path-quoting` for quoting review, `service-logons` for account-class review, `service-dlls` for registered DLL presence and signature status, `service-triggers` for trigger configuration, `service-recovery-policy` for recovery actions or `service-transitions` for a bounded repeated pending-state observation through the CLI.

**Event Log** checks the Windows Event Log service and four core diagnostic channels. The display distinguishes disabled channels from logs that are approaching their configured size limit. A retained log near capacity requests review because it can stop accepting new records. Circular and automatic-backup logs explain their overwrite or rotation behavior instead. Optional automatic repair applies only to an eligible stopped Event Log service and verifies its stable state. A separate channel selector and confirmation can enable one exact disabled unmanaged diagnostic channel after fresh checks. KillerBench saves preparation, then repeats exact channel, policy and administrator evidence immediately before the request. Changed, unavailable or canceled final evidence runs no command and closes the prepared guard. Only a request that may have reached Windows remains pending for no-repeat reconciliation. It preserves retention, automatic backup, maximum size, permissions, existing events and every other channel. CLI: `workflow eventlog --json`, `event-channels`, `event-channel-enable CHANNEL [--execute]` and `event-channel-enable-recover`.

**Focused servicing services** provide direct BITS service, Cryptographic Services and Windows Modules Installer checks without running component-store or system-file scans. Each can start only an enabled, stopped exact service after automatic repair is selected and fresh dependencies and machine prerequisites pass. Existing transfers may resume, as may catalog, certificate, update and component-servicing operations. Jobs, certificates, keys, catalogs, packages, component-store content, policy and startup types remain unchanged. CLI keys are `bits-service`, `cryptographic-service` and `modules-installer-service`; add `--auto-repair` only when service availability is required.

**Focused diagnostic services** provide direct Diagnostic Policy Service and Windows Error Reporting checks. Existing troubleshooting and error-reporting activity may resume under current policy. Troubleshooting data, report archives, dumps, consent and upload policy, service permissions and startup types remain unchanged. CLI keys are `diagnostic-policy-service` and `error-reporting-service`; add `--auto-repair` only when service availability is required.

**Event collection and remote access services** provide direct Windows Event Collector and Remote Access Connection Manager checks. Event Collector also lists up to 256 exact subscription names while retaining the bounded command evidence. Remote Access lists up to 128 current-account VPN profiles with server, tunnel type, authentication modes, split-tunneling choice, credential-retention flag and reported connection status. Passwords, certificates and keys are excluded. These inventories do not verify source reachability, authentication, delivery, freshness or connectivity. Each service can start only when enabled and stopped after automatic repair is selected and fresh dependencies and machine prerequisites pass. Existing event subscriptions, dial-up requests and VPN requests may resume under their current configuration. Subscriptions, forwarded events, connection profiles, credentials, routes, adapters, authentication settings, policy, service permissions and startup types remain unchanged. CLI keys are `event-collector-service` and `remote-access-service`; add `--auto-repair` only when service availability is required. Use `vpn-profiles` for the focused read-only profile inventory.

**Remote Desktop Services** reports local enablement, Network Level Authentication, the configured RDP-Tcp port and matching machine policy values. It also retains up to 200 connection-manager and 200 local-session-manager Operational events from the last seven days, grouping warning, error and critical records by event ID and level before checking exact TermService state. Normal summaries omit accounts, client addresses, session identities, certificates and authentication payload while raw XML remains retained evidence. Empty complete history is informational. Malformed, duplicate, unexpected-provider, inaccessible and capped evidence remains Unknown. Registry and historical observations do not prove effective policy, listener binding, firewall access, certificate identity, permissions, authentication, reachability or current session state, and they never select a repair. Optional recovery starts the service only when it is enabled and stopped and fresh dependency, administrator and restart checks pass. An existing listener may become reachable immediately under current policy, NLA, firewall rules and permissions. KillerBench does not enable Remote Desktop, create a listener, open a firewall rule, grant account access, replace a certificate, change a port, disconnect a client or alter a session. Stable service state does not prove remote reachability, authentication or session creation. CLI: `workflow remote-desktop-services --auto-repair --json`; omit `--auto-repair` for diagnosis only.

**Windows Remote Management** inventories up to 32 registered HTTP and HTTPS listeners, then retains up to 200 Operational events from the last seven days and groups warning, error and critical records by event ID and level before checking exact WinRM service availability. Listener summaries show configured address, effective port, URL prefix, enabled state and whether HTTPS certificate configuration is present. Exact listener identities and certificate thumbprints remain in raw evidence. Account, process, endpoint, operation and authentication event details also stay in raw evidence and are omitted from the event summary. Inaccessible or incomplete inventory remains Unknown and is never interpreted as no listeners. Configuration and historical records never select a repair. Optional recovery starts WinRM only when enabled and stopped and fresh dependency, administrator and restart checks pass. Existing WS-Management listeners may become reachable immediately under current authentication, certificate, firewall, TrustedHosts and policy settings. KillerBench does not create a listener, open a firewall rule, add a trust entry, replace a certificate, collect a credential or start a remote session. Stable service state does not prove listener reachability, authentication or remote command execution. CLI: `workflow windows-remote-management --auto-repair --json`; omit `--auto-repair` for diagnosis only. Use `winrm-listeners` for the focused read-only registration inventory.

**Scheduled task drafts** remain separate from the Task Scheduler service repair. The desktop Scheduled tasks panel and `task-register PLAN.json YYYY-MM-DD [--execute]` preview registration by default. Desktop creation requires its separate confirmation. The main evidence display and CLI stderr show eligibility, preparation, final check, creation, read-back and completion stages while the CLI keeps its JSON result on stdout. The guarded path supports only an elevated, highest-privilege Local System plan with a stable validly signed executable, an existing task folder and an absent exact target. It prepares durable evidence, repeats every eligibility check, uses create-only registration and reads the exact definition back. A verified task remains disabled and is never run. If creation was interrupted, use **Check interrupted registration** or `task-register-recover PLAN.json`. Recovery reads the exact current definition and closes the guard only when it matches the journaled plan and calendar boundary. It never sends another creation request or changes the task. KillerBench does not create a folder, replace, enable, retry or delete a task.

**Windows Search** checks and optionally starts the enabled WSearch service with bounded running-state verification. It also reads current SystemIndex activity and recent Search event history. Common problems includes the same read-only catalog and event evidence. It preserves the index, indexed locations and startup configuration. Starting it may resume indexing activity. Index rebuilding and search-result verification are not included. The CLI command is `workflow search --json`.

**System Restore points** lists the local restore points Windows currently reports, with bounded descriptions, types, sequence numbers and UTC creation times. The same read-only inventory is included in Common problems and is available through `workflow system-restore --json`. An empty list does not prove that System Protection is disabled or broken. Select **Prepare one restore point**, enter a description, choose a reason and press GO for a preview. Select the automatic action checkbox before GO to request it after a fresh complete inventory and administrator check. KillerBench saves pending evidence first, then repeats the inventory, supported-client, frequency and administrator checks immediately before the request. A newly recent point, changed prerequisite, canceled check or unavailable final inventory produces a no-request result and closes the prepared guard. A dispatched request must verify one new exact sequence afterward. Interrupted and uncertain dispatched requests are reconciled by rereading inventory without requesting another point. CLI commands are `restore-point DESCRIPTION [ModifySettings|ApplicationInstall|DeviceDriverInstall] [--execute]` and `restore-point-recover`. KillerBench does not enable protection, delete or apply points, and an inventory entry does not prove that a future restore will succeed.

**Windows Recovery Environment** reads the current Windows RE state, configured location and BCD identifier through `workflow windows-recovery --json`. A disabled exact state can offer optional automatic enablement through the shared Engine recipe. KillerBench checks exact eligibility before creating a repair journal, checks it again immediately before the command, runs bounded `reagentc.exe /enable`, then requires a separate `/info` result that reports Enabled. A state change to Enabled skips the command. Localized, unrecognized, changed or incomplete evidence defers the command and cannot verify the change. Either no-dispatch outcome records an explicit skip and closes the prepared recovery marker because enablement never started. The existing recovery image and location are preserved. KillerBench does not download, relocate or replace an image, boot into recovery or restart Windows. Enabled status does not prove that the recovery image can boot or repair the PC. Native execution remains a disposable-machine validation item.

**Certificate expiration** reviews the machine and current-user personal certificate stores for expired, next-30-day expiry and not-yet-valid certificates. It is available under Security, through `workflow certificates --json` and as a Common problems scope. It retains thumbprints and validity evidence for exact review but does not test trust chains, revocation, bindings or private-key usability. No certificate, trust setting, enrollment or private key is exported, changed or deleted.

Network diagnostics also inspect adapter Device Manager codes using the same bounded device collector as Audio. Missing drivers, disabled adapters and startup failures receive distinct findings before DHCP recovery. Virtual and disconnected device records remain visible as observations; no adapter is enabled, removed or reset automatically. A clean device code does not establish network reachability.

**Audio** collects audio/media Device Manager status, then checks Audio Endpoint Builder before Windows Audio, optionally starting stopped, enabled services with bounded running-state verification. KillerBench does not inspect file contents, run cleanup or change Storage Sense settings.

Storage also reads the exact built-in Storage Sense scheduled task state and runtime history. It reports action count, last result, missed runs and last-run local time without collecting action contents or trigger details. A failure-class result on the enabled task requests review. When Windows recognizes the exact code, KillerBench also shows the installed system message as a correlation, while making clear that it does not establish why the task returned it or whether cleanup was needed. Use `killerbench-cli storage-sense-task` for the same read-only result. KillerBench does not run the task, change its schedule or remove files.

The same bounded task inspection covers the separate built-in SilentCleanup task. Use `killerbench-cli disk-cleanup-task` to see its state, action count, runtime history and any installed Windows message for an exact failure-class result. That message is supporting evidence, not a task-specific diagnosis or proof that cleanup failed. KillerBench does not run SilentCleanup, alter its schedule or remove files.

Storage also checks the exact built-in Windows disk diagnostic collector and resolver tasks. Use `killerbench-cli disk-diagnostic-tasks` to see both states and runtime histories. Use `killerbench-cli disk-diagnostic` for the two tasks, the three exact DiskDiagnostic Operational channels and their combined correlation. Event collection retains at most 200 records per channel from the last seven days, groups warning, error and critical records by event ID and level, and keeps hardware identifiers out of ordinary summaries. Incomplete evidence remains unknown before historical attention is considered. Disabled or never-run task history and empty event history can be normal and do not prove a disk is healthy, failing or repaired. KillerBench does not run either task, inspect its action, test or repair a disk, format storage, change a schedule or alter an event channel.

Storage and Full system scan also summarize current Storage module jobs. Use `killerbench-cli storage-jobs` to review grouped job names, state, foreground or background status, maximum progress and maximum elapsed time. Suspended, shutting-down, failed and terminated work requests review. Completed work does not prove that its underlying storage operation succeeded. Object IDs, unique job IDs, paths and provider payloads are excluded. KillerBench does not start, stop, resume, remove or change a job or any storage object.

Storage and Full system scan also read per-volume disk quota defaults. Use `killerbench-cli disk-quotas` to review whether each drive-letter volume disables, tracks or enforces quotas, along with its default warning and limit and notification settings. Individual user quota rows, account identities and usage are excluded. The snapshot can explain storage restrictions but does not prove that any user reached a threshold. KillerBench does not change quotas, notifications, volumes, files or policy.

Windows Update and System Files also read the online Windows reserved-storage state. Enabled, disabled and in-use states remain servicing context because managed environments can intentionally control the setting. Use `killerbench-cli reserved-storage` for the same read-only result. KillerBench does not enable or disable reserved storage.

Those workflows also inventory online Windows capabilities such as OpenSSH, RSAT, language features, OCR and media components. Pending or partially installed capability states request review without selecting installation or removal. Use `killerbench-cli windows-capabilities` for the same read-only result. KillerBench does not download, install, remove, stage or restore a capability.

Storage and backup readiness also inspect VSS shadow-storage allocation. Any finite association using at least 90% of its configured maximum asks for review of retention, recent snapshot loss and available capacity. Unlimited associations, used space and allocated space remain separately visible. Missing or inconsistent evidence stays Unknown. `killerbench-cli shadow-storage` returns the same result. This check never resizes the differential area or creates, deletes or opens a snapshot.

Storage also offers drive optimization as a separate choice. GO first confirms the selected volume, filesystem, provider health and media type, then performs read-only analysis. Automatic repair consent enables the selected operation only after fresh prerequisites. After durable preparation, KillerBench repeats exact identity, health, media compatibility, analysis and administrator evidence immediately before the command. Changed, incomplete, unavailable or canceled final evidence runs no optimization and closes the prepared guard. Windows recommended lets Windows select the proper supported method. Retrim requires confirmed solid-state or thin-provisioned media, and Defragment requires a confirmed hard disk. Only an operation that may have reached Windows remains pending and is reconciled without repeating it. Successful execution still requires exact-volume reinspection and another complete analysis. KillerBench does not alter the optimization schedule or restart Windows. CLI commands are analysis-first `volume-optimize D: [Recommended|ReTrim|Defragment] [--execute]` and `volume-optimize-recover`. Native execution remains unvalidated.

The recipe catalog is available through `RecipeCatalog.All` and `killerbench-cli recipes`. Workflows execute versioned recipes through `RecipeEngine.RunAsync`, retaining recipe IDs, versions, diagnoses and repair outcomes in their journal. Dependencies must appear before dependent recipes; invalid graphs are rejected before any check runs. Independent recipes can continue when another branch fails. This is an initial catalog, not comprehensive Windows repair coverage.


## Windows Update capture

Click **Scan Windows Update** for an on-demand, read-only collection. The scan reads CBS.log, DISM.log, Panther and rollback setup logs, WindowsUpdateClient/Operational, BITS/Operational, Setup, Application, and update/servicing providers in System. It also captures update-service states, system disk free space, uptime, pending-reboot indicators and selected Windows Update policies. Additional sources are available as evidence; the existing CBS, Setup and servicing-event rules do not diagnose every new source. The overview shows the machine, OS, process elevation, capture times, source coverage and grouped findings. Each finding has one **Show evidence** action that opens its first reference and lists related lines. Select **Windows Update capture** in the sidebar to return to all findings.

Each source has a 15-second limit; the scan has a two-minute limit. **Stop** or Esc keeps completed sources and records skipped ones. Missing files, denied access, failures and truncation are separate outcomes. The app requests administrator access at startup. CLI scans work without elevation where access permits. Capture does not change services, update settings or log configuration.

Text snapshots retain the first 1,000,000 characters, not the latest tail. Later entries in oversized logs and archived CBS files are not analyzed. Event queries retain the newest 200 events per channel from the preceding seven days, preserve raw XML and record IDs, and mark an exceeded event limit. Event SystemTime is retained as recorded, normally UTC; text-log time zones remain unknown. Sources are collected sequentially and are not an atomic snapshot. KB-EVENT-001 groups error/critical events from Windows Update and Servicing as review leads.

Full system scan plus the Windows Update and System Files workflows also run a separate automatic newest-log review. It inspects up to 1,000,000 characters from the tail of each present CBS, newest plain-text CBS archive, newest compressed CBS archive, DISM and fixed Panther or rollback Setup log, with 15 seconds allowed per text file. CBS archive discovery stays in the fixed CBS directory and examines at most 4,096 candidates. A compressed archive is limited to 256 MiB and its single expected log member to 512 MiB. Extraction runs for at most 30 seconds in a unique temporary directory that is removed after reading. Missing optional archive and upgrade logs are normal. Access failures, malformed input and incomplete coverage remain visible without hiding other sources. Supported historical findings request review but cannot authorize a repair. Run `killerbench-cli servicing-logs` for the same read-only analysis without starting a workflow.

**Save capture** writes a local `.kbench` JSON file with machine identity, source paths, coverage and the retained raw evidence. **Open capture** works without the original source files and re-evaluates evidence with the installed rules. With the same rules, findings and references are reproduced; future rule changes may change findings. The format accepts up to 24 sources and 64 MB. **Export report** from the capture overview exports all source reports; from an individual source it exports that source only. Reports contain paths and excerpts; captures contain full retained evidence. Neither is uploaded. Starting a scan or opening another capture replaces the displayed session, so save a capture you want to retain first.

```powershell
dotnet run --project Cli/KillerBench.Cli.csproj -- scan --output "C:\captures\update.kbench" --json
dotnet run --project Cli/KillerBench.Cli.csproj -- open "C:\captures\update.kbench" --json
```

Create the destination folder first. The CLI requires a new output filename. Progress goes to stderr and JSON to stdout. Scan/open exit codes are 0 for completed coverage, 3 for partial collection, 1 for failure, 2 for invalid arguments, and 130 for cancellation or overall timeout. A canceled scan saves completed evidence before returning. No exit code certifies machine health.

The shared API is `Capture.CollectAsync(IEnumerable<IEvidenceCollector>, progress, cancellationToken)`, with `WindowsUpdateCollectors.Create()` supplying Windows collectors. `Capture.SaveAsync`, `OpenAsync`, `Analyze`, and `ReportJson` support offline investigations. Custom collectors must honor cancellation. Windows event queries use the built-in [wevtutil query command](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/wevtutil); no new package dependency is required.

## Automated workflows

Service recovery flows are also available: **Printing service**, **Windows Time service**, and **Windows Installer service** (CLI names `printing`, `time`, and `installer`). With auto-repair enabled they start the selected stopped, enabled service and query its state afterward. The final native gate repeats service, dependency and executable-registration eligibility immediately before start. A service that became Running records a skipped start, and other lost eligibility records an explicit deferral. Both close the prepared recovery marker because no command ran. Disabled, missing, paused, transitioning, or unrecognized service states require attention instead. A stopped demand-start service can be normal; these are explicitly selected availability checks, not proof of a fault. They preserve startup configuration, print queues, time sources and installer settings. Verification proves only that the service reached Running, not that a print job, time synchronization or installation succeeded. These flows share the local journals and simulated repair checks. No service was started during development validation.

Windows Time source configuration is separately consented. Custom peers are limited to standalone machines. Domain hierarchy is limited to domain members that are not domain controllers. Both require administrator access, confirmed unmanaged policy, two matching fresh checks, a durable recovery record and one final unchanged check immediately before the command. Changed or unavailable final evidence sends no command and archives the prepared no-change record. Domain hierarchy configures `NT5DS`, requests rediscovery and verifies the stored mode plus reported synchronization. Desktop GO and `time-configure --execute` check pending evidence before any new change. Recovery reports no pending record, verified, still unverified or invalid retained evidence and never repeats configuration or synchronization. Windows status does not establish absolute clock accuracy, and native domain validation remains on the VM checklist.

Choose a workflow in the main selector, configure its visible options, and click **GO**. Diagnosis is the default. **Auto-repair confirmed issues** permits supported repairs in eligible workflows. Vitals, Privacy and BitLocker inspection do not repair; cleanup and update installation have separate explicit controls. KillerBench requests administrator access at startup.

The Network workflow compares each default route's route metric with its exact interface metric and displays the effective total Windows uses for preference. Equal lowest totals and retained routes that are not reported Alive request review without offering an automatic metric change. Automatic metric state remains visible. Use `killerbench-cli route-priority` for the same bounded read-only result.

Network also reports whether Windows connectivity classification can use active probing and passive polling, plus whether its built-in web or DNS probes are overridden. Probe destinations and expected content are excluded from saved evidence. If both classification paths are disabled, KillerBench requests policy-owner review because Windows Internet labels may be limited or unavailable. This does not test Internet access or change connectivity policy. Use `killerbench-cli ncsi-policy` for the same read-only result.

Network also summarizes IPv4, IPv6, Microsoft network client and file-sharing bindings for visible adapters. Both IP protocols disabled on an active hardware adapter requests review. One disabled IP family and disabled sharing-related bindings remain descriptive because these choices can be intentional. Use `killerbench-cli adapter-bindings` for the same read-only evidence. KillerBench does not enable, disable or reset a binding.

Network also reads cumulative byte, packet-error and discarded-packet counters from visible adapters that expose statistics. Any nonzero error or discard counter requests review, but does not establish a current outage because counters can span the adapter or computer uptime. Compare repeated snapshots with link, driver and switch-port evidence. Use `killerbench-cli adapter-statistics` for the same read-only result. KillerBench does not reset or reconfigure an adapter.

Network also compares the configured IPv4 and IPv6 dynamic TCP ranges with aggregate distinct local-port usage. Usage at or above 80% requests review, but does not identify a leaking process or prove port exhaustion. Reports retain counts only and exclude endpoints and process identities. Use `killerbench-cli tcp-port-pressure` for the same read-only snapshot.

Windows Update checks current prerequisites and runs component-store and system-file checks in order. It also summarizes current Delivery Optimization jobs by documented status and aggregate byte totals without retaining file IDs, source URLs, cache hosts, peer addresses or caller identities. A separate policy check retains recognized nonnegative numeric settings and the names of configured group, cache-host and cache-drive settings from classic and current Policy CSP surfaces. Group IDs, cache hosts, cache-drive values and provider identities are excluded. Download mode 100 requests policy-owner review because Microsoft deprecated Bypass on Windows 11; other configured values remain context and never authorize a reset. Confirmed corruption selects the matching repair, followed by verification. Failed verification stops dependent work. An exact paused Delivery Optimization service can be continued when automatic repair is selected. A paused transfer job remains read-only context and does not authorize that service action. The recipe repeats the paused-service check immediately before `sc.exe continue DoSvc` and verifies stable Running evidence. A state change to Running records a skipped continue step, while any other lost eligibility records a no-dispatch deferral. Both close the prepared recovery marker because no continue request ran. It does not start an idle stopped service or change its cache, startup type, bandwidth, peer, update-source or managed-policy settings. Historical logs, unknown output, failed commands and truncated results never select a repair. Pending restart, low free space (a conservative 5 GB guard) or missing administrator rights defer servicing. Disabled services and managed update policies are reported without changing them. This workflow checks servicing health, current transfer activity, configured policy surfaces and selected service state; it does not install an update or prove that Windows Update now works. CLI: `killerbench-cli delivery-optimization-activity` and `killerbench-cli delivery-optimization-policy`.

Vitals reports restart, free space and service configuration. Common problems also includes read-only Windows licensing state, core event-channel settings, Reliability Monitor history, WHEA history, SetupAPI driver-install failures correlated with the current Plug and Play inventory, crash-report paths correlated with configured and discovered dump-file metadata, Domain, Private and Public firewall profile settings, Windows Update execution, applicability, policy, source registration, operation history and Delivery Optimization context, the Windows volume dirty bit, current Installer activity, and Windows Search catalog and event evidence. Historical findings remain evidence for review and never authorize driver or hardware changes. Dump contents are never opened. Disabled firewall profiles require policy-owner review; rules and settings are not changed. Update context does not install updates or alter update sources, policy, services or Delivery Optimization. Installer activity does not stop processes or alter transaction markers. Search evidence does not resume, rebuild or delete the index. Dirty-bit inspection does not schedule repair or restart and does not establish filesystem or media health. Licensing evidence omits product keys and does not attempt activation. Channel settings do not prove that every expected event is being recorded. Network inspects current IP address state and origin, exact default-route gateways and DNS configuration without resetting networking. APIPA, duplicate non-link-local addresses and non-Preferred Windows address states request review. It sends bounded ICMP probes only to recorded next hops, then correlates Windows connectivity labels with exact interface-family routes and gateway evidence. A missing reply can result from blocked ICMP and does not prove an outage. VPN and virtual paths can lack ordinary connection profiles and remain identified as context. Filter adapters without IP bindings are informational. Network results do not prove Internet access or working DNS resolution. Use `killerbench-cli ip-addresses` or `killerbench-cli gateway-check` for either evidence set without running the full workflow.

The Network tool can run a guarded local DNS cache repair for one exact hostname when automatic repair is selected. Only `HostNotFound` or `NoData` evidence is eligible. The shared recipe engine repeats the lookup, records preparation, then checks the same hostname again immediately before flushing the local resolver cache. If it resolved, the evidence changed, final evidence became unavailable or the final check was canceled, the run records that no flush occurred and closes the prepared guard. Otherwise it dispatches the flush and verifies the same hostname, so the app and `workflow network --host HOST --auto-repair` use the same decision and result. An interrupted or unconfirmed dispatched flush retains its pending guard for read-only reconciliation. It does not change DNS servers, network adapters, hosts files or authoritative records. When an interrupted operation is pending, GO rechecks and records the same hostname without repeating the flush. Complete exact-host evidence archives the result, while incomplete evidence keeps the guard. `killerbench-cli dns-cache HOST` previews the standalone Engine flow; add `--execute` to authorize it. `killerbench-cli dns-cache-recover` also exposes the no-repeat review directly. A failed verification remains unresolved and native execution still requires disposable-machine validation.

The shared API is `Workflows.RunAsync(kind, autoRepair, journalFolder, progress, cancellationToken)`. CLI: `killerbench-cli workflow <update|files|vitals|network> [--auto-repair] [--json]`. Exit 0 means no unresolved issue in checked scopes, 3 means attention required, 130 means stopped, 2 means invalid arguments, and 1 means a startup or journal error. Progress goes to stderr. Each run saves a JSON journal under local application data in KillerBench/Workflows, including decisions, bounded integrity-check output and repair results. Stop waits for the current servicing command. Unknown or localized SFC output requires review. No automatic restart or rollback is performed.

Automated tests cover clean checks, repair selection and ordering, diagnosis-only mode, blocked prerequisites, failed verification, unknown output, cancellation, journals, network configuration and workflow controls. Actual servicing repairs still require disposable-VM validation.

### Computer name

Changed, unavailable or canceled final evidence produces a no-request result and closes the prepared guard. Only a request that may have reached Windows retains pending recovery. ### BitLocker options

Select **BitLocker (BERET)** to choose a volume, operation, encryption method, used-space-only and recovery destination/path. GO inspects unless a matching confirmation is selected. Backup Recovery with a File destination can discover an existing recovery protector and create a new restricted file. Resume Protection can resume an exact fully encrypted, unlocked volume whose protection is Off. Encrypt is limited to an unmanaged, fully decrypted and unlocked NTFS operating-system volume with a ready TPM, exactly one existing TPM protector and one selected recovery-password protector. KillerBench writes and verifies a new recovery backup outside the protected volume before it saves durable encryption intent. It then repeats volume identity, filesystem, volume type, TPM, policy, conversion, lock, protector, restart and administrator checks immediately before one request. ### Privacy options

Select **Privacy (SHADE)** and check the areas to inspect. All start unchecked. GO saves a read-only snapshot for the selected areas. Camera and microphone, clipboard history and sync, app activity, and typing and inking personalization are separate choices. CLI: `privacy-plan --select Camera --select InputPersonalization --inspect`. Without `--inspect`, the command describes the selected areas only. It does not inspect cache contents, and recorded values do not establish effective permissions or policy ownership.

Clipboard history also has a separate **Inspect only**, **Turn on** or **Turn off** choice. A later user or policy change, unavailable final evidence or cancellation before dispatch runs no write and closes the prepared guard. ### Servicing activity monitor (PEEK)

The Windows Update line identifies the latest recognized download, ready, install, completion, failure or rollback transition with its local update title and exact result code when present. A recognized transition from the prior two minutes also drives the high-level live state before process-only fallback. Older transitions remain bounded history and do not replace a later current success.

The separate **Windows Update scheduled task** option adds bounded state, missed-run and retained-result evidence for the exact built-in Scheduled Start task. It never starts, recreates or changes the task, and missing or disabled state can be intentional on some Windows or managed configurations.

Choose **Diagnostics**, then **Servicing activity monitor (PEEK)**. Set the refresh interval from 1 through 60 seconds and the number of snapshots from 1 through 120. Recent Windows Update events, update history, servicing service states, restart indicators, Panther setup activity, compatibility block counts, storage, power and BitLocker readiness, current-account background transfers, Delivery Optimization activity, and Windows Installer activity can be included independently. GO streams each evidence stage into the main display. As soon as a snapshot completes, the console shows its overall state, active or idle servicing status and a bounded one-line summary for every selected check. Its **Live servicing state** line prioritizes recent classified Setup activity, then observed Setup, component-servicing, update-orchestration and Installer activity, pending restart or a qualified idle state. It does not report a progress percentage or infer completion, a stall or a cause. The completed sequence is then retained as a session source with the full check details. The monitor always groups a fixed set of Windows Update, Setup and servicing processes by name, including Windows 11 Installation Assistant, Setup, SetupHost, SetupPrep, wuaulcore, TiWorker, TrustedInstaller, MoUsoCoreWorker, UsoClient, WaaSMedicAgent and DISM. It retains bounded counts, aggregate working memory and the oldest activity age for each group. After the first refresh, it also reports aggregate CPU across the interval. Process IDs are used only transiently in memory for CPU correlation and never enter evidence, reports or journals. Command lines, users and paths are also excluded. Later snapshots report transfer-byte changes only for the same BITS job identities and nondecreasing Delivery Optimization totals. Changed job sets and reset counters are reported as not comparable. Setup summaries retain only fixed source labels, times, sizes, recognized feature-upgrade codes and a classified compatibility scan, package download, in-place upgrade, finalize or generic Setup mode. Documented `0xC190` results include their exact symbol, meaning and next diagnostic scope. Unknown codes remain visible without a guessed meaning, and compatibility-only completion stays informational. The original SetupHost command line is excluded. Compatibility summaries retain block counts without application or driver identities. Readiness uses a focused battery query that retains only charge and status, plus system-volume capacity and BitLocker evidence. Background-transfer evidence is account-scoped, and queue names do not prove Windows Update ownership. Delivery Optimization retains only status counts and aggregate byte totals without file, source, cache host, peer or caller identities. Installer activity retains only the msiexec process count and in-progress marker. A visible process, resource total, transfer, event or recent log write is activity evidence, not proof of progress, completion, a stall or a fault. Zero observed movement does not establish a stall. Stop cancels the next collection or refresh wait. CLI embedders can collect up to 120 snapshots with `servicing-monitor --refresh SECONDS --samples COUNT` and the matching `--skip-*` options, or query one documented Setup result with `setup-code DECIMAL_OR_0xHEX`. No update, setup, transfer, service, process, policy, restart, encryption or repair action is requested.

### Available updates

In the app, run discovery and expand **Select updates after discovery**. Select individual rows, choose whether to include updates that may need a restart, and press **Preview selected**. A feature upgrade requires the separate **Allow one offered Windows feature upgrade** option, restart consent, and exactly one selected update. The exact feature-upgrade category supplied by Windows identifies it; title text is never used. This uses the shared planning rules and shows blockers in the evidence console. **Install selected** starts fresh checks and installs eligible selections with live status and a journal. The old selection is cleared afterward. No automatic restart is scheduled. Native installation still requires disposable-machine validation.

The Engine `UpdateExecution` coordinator records prepared operations, outcomes and readiness blockers in a journal. After writing the pending marker, it repeats machine readiness and the exact selected update's search scope, identity, revision, license, interaction, beta, impact and restart-policy checks. Changed or unavailable final evidence sends no installation request and archives the prepared no-install record. Unverified or restart-required dispatched operations retain a pending marker that blocks another attempt in the same journal folder. `UpdateReconciliation.TryResolveAsync` archives that marker only after verifying the exact revision is installed and the machine is ready; unknown or not-installed states remain blocked. `WindowsUpdateExecutionHost` implements single-update download, installation and exact-revision verification with a one-hour process bound. App and CLI execution are wired. Tests substitute COM objects; native installation still needs disposable-machine validation.

Prepare a fresh installation preview with `killerbench-cli update-plan --select GUID:REVISION --drivers --allow-restart-required --json`. Repeat `--select` for additional identities from discovery; category switches match discovery. Restart allowance never schedules a restart. Shared planning rejects incomplete discovery and changed or duplicate selections, and reports license, interaction, beta, exclusive-installation and restart blockers. Add `--execute` for installation through fresh prerequisites and a durable journal. `killerbench-cli update-recover` checks an interrupted operation without installing or retrying it.

Discovery also retains update classifications, beta status, installation impact, possible user interaction and reboot behavior. Missing or malformed metadata is marked unavailable while preserving the update identity. These are prerequisites for future installation planning, not authorization to install. Metadata follows [IInstallationBehavior](https://learn.microsoft.com/en-us/windows/win32/wua_sdk/iinstallationbehavior-properties) and [IUpdate](https://learn.microsoft.com/en-us/windows/win32/wua_sdk/iupdate-properties).

Available updates first inventories the Windows Update Agent services already registered on the machine, reads the exact built-in Scheduled Start task and its bounded runtime summary, reads the newest 100 operation-history entries, then checks whether the selected source is ready before searching with the software and driver choices. Configured source preserves the machine's default selection. Windows Update selects the public Windows source. Microsoft Update requires its service to already be registered; missing or incomplete registration evidence stops discovery without changing enrollment. The source evidence identifies Windows Update, Microsoft Update, managed status and Automatic Updates registration without collecting service URLs or changing enrollment. The scheduled-task evidence complements PEEK activity and history without starting or recreating the task; missing or disabled state can be intentional on some Windows and managed configurations. History retains exact update identity, revision, UTC time, install/uninstall operation, result and HRESULT. Incomplete or failed outcomes from the last 30 days request review; older failures remain historical observations. Recognized recent failures automatically run relevant read-only follow-up checks for the current execution context, Windows applicability context, Windows Update services, BITS, Delivery Optimization, network configuration, proxy configuration, restart state, Installer activity, managed update policy or component servicing health. Routes are stable and deduplicated when several errors request the same check. A failed follow-up does not hide the other results, and no follow-up can expose a repair. The execution-context check retains elevation and desktop-session status without account identifiers, but it cannot identify the context of a historical operation. The applicability check retains Windows edition, build and architecture, but still requires the exact update's requirements for comparison. Full system scan and the Windows Update workflow also summarize bounded current Delivery Optimization job counts and byte totals, identify recognized classic and Policy CSP settings, then measure bounded file counts and sizes for the fixed SoftwareDistribution Download and DataStore areas. Transfer identities, sensitive policy values, provider identities, cache filenames and file contents are excluded. Current activity, configured policy and cache size do not establish corruption or authorize cleanup. A failed current search retains its exact HRESULT and uses the reviewed error catalog when recognized. Unknown codes remain visible without a guessed diagnosis. Current search failures return no installable updates and never select a repair. GO discovers updates; installation uses the separate selected-update action. `killerbench-cli servicing-logs`, `killerbench-cli delivery-optimization-activity`, `killerbench-cli delivery-optimization-policy`, `killerbench-cli update-cache`, `killerbench-cli update-services`, `killerbench-cli windows-update-task`, `killerbench-cli update-history`, `killerbench-cli update-context` and `killerbench-cli update-applicability` run those checks separately without automatic follow-ups. Registration, scheduled-task history, update history, historical log findings, current transfer activity, configured policy and cache size do not prove reachability, current applicability or current health.

Select **Third-party apps** before GO to run a separate application update search beside any selected Windows Update categories. It uses typed `Microsoft.WinGet.Client` package objects under PowerShell 7 and retains at most 4,096 installed-package observations, 256 candidates and 64 available versions per candidate. Missing provider support, malformed identities, duplicate packages, provider errors and any exceeded bound remain Unknown. This provider can omit packages it cannot correlate and an empty list does not prove every application is current. The desktop keeps Windows and application candidates in separate selectors. Choose one application, one offered version and agreement acceptance before Install selected becomes available. The Engine and CLI expose the same boundary through `third-party-updates`, `third-party-update ID SOURCE VERSION [--accept-agreements] [--execute]` and `third-party-update-recover`. Execution repeats complete discovery after durable preparation, never uses upgrade-all, force, security-bypass or automatic-reboot options, and requires fresh exact installed-version verification. Recovery checks uncertain pending evidence without retrying the update. Native disposable-machine validation remains unfinished.

Update workflows also report managed feature update targeting, deferral, pause-date and safeguard opt-out settings. A target release records policy intent only. It does not prove that Windows currently offers the release or that the device is compatible. Disabling safeguard holds requests administrator review because it can bypass protection for known compatibility issues. KillerBench never changes these settings. Run this check separately with `killerbench-cli feature-update-policy`.

CLI: `killerbench-cli workflow updates --drivers --source MicrosoftUpdate --json` searches software and drivers from an already registered Microsoft Update service. Use `Configured` or `WindowsUpdate` for the other source choices, and add `--no-software` to search drivers alone. At least one category is required. The Engine API is `UpdateDiscovery.SearchAsync(UpdateSearchOptions)`. Searches have a five-minute process bound and retain up to 500 update identities, revisions, titles and download/license states. Failed, timed-out or incomplete searches do not claim that the machine is up to date. Tests substitute the update agent and validate source, category and partial-result handling.

Before GO, use the TPM, Secure Boot and virtualization checkboxes to select the hardware checks. Unchecked providers are not queried and their report entries say Not selected. Defender signature checks remain included. CLI equivalents are `--skip-tpm`, `--skip-secure-boot` and `--skip-virtualization`, accepted only for `workflow defender`. The Defender tool defaults to **Diagnosis only**. Select **Quick scan** or **Full scan** to make GO show current eligibility. Enable **Start the selected scan when I press GO** only when that exact scan should begin. CLI equivalents are `defender-scan Quick|Full [--execute]` and `defender-scan-recover`.

Security diagnosis also summarizes effective AppLocker executable, Windows Installer, script, DLL and packaged-app collections. Hardware-status references: [Get-Tpm](https://learn.microsoft.com/en-us/powershell/module/trustedplatformmodule/get-tpm?view=windowsserver2025-ps), [Confirm-SecureBootUEFI](https://learn.microsoft.com/en-us/powershell/module/secureboot/confirm-securebootuefi?view=windowsserver2025-ps), and [Win32_DeviceGuard status values](https://learn.microsoft.com/en-us/windows/security/hardware-security/enable-virtualization-based-protection-of-code-integrity).

### Configurable file cleanup

Windows Temp and Windows SystemTemp are independent selections. Windows SystemTemp is limited to the fixed `%SystemRoot%\SystemTemp` root and is available through the CLI with `--system-temp`.

Select Cleanup, choose temporary files, thumbnail caches, icon caches, shader caches, browser caches, archived Windows error reports, application crash dumps and/or Windows minidumps, and set the minimum age from 1 to 365 days. GO previews by default. Thumbnail and icon cleanup are separate selections that include only `thumbcache_*.db` or `iconcache_*.db` in the standard current-user Explorer cache folder. They exclude Explorer history, recent items, saved searches and other files. Browser discovery searches default current-user Chrome, Edge, Brave, Firefox and Opera cache folders with bounded profile coverage; custom locations are not searched. Cookies, logins and profile settings are outside those targets. Error-report cleanup covers only the current user's standard WER ReportArchive and ReportQueue folders. Application dump cleanup covers only the current user's standard CrashDumps folder. Windows minidump cleanup covers only `%SystemRoot%\Minidump`, normally requires administrator access, and leaves `%SystemRoot%\MEMORY.DMP` untouched. These separate targets do not remove event history, but they discard local evidence that may be needed to diagnose application failures. The separate permanent-removal checkbox enables deletion of up to 100 retained candidates per target per run; it bypasses the Recycle Bin and has no undo. Older creation, modification and access timestamps are required, but timestamps alone do not prove that an application no longer needs a file. Cache rebuilding can slow initial loading.

Removal recollects the selected targets, opens candidates exclusively, rejects changed paths, links, protected files and changed metadata, and requests deletion through the checked file handle. Each attempt is journaled before mutation and each outcome afterward. Path absence is checked after the handle closes. Unverified results are not retried automatically. Partial collection, remaining candidates and cancellation are reported explicitly. Stop is checked between individual files and the removal loop stops scheduling work after two minutes; a single operating-system file call is synchronous.

CLI: `killerbench-cli cleanup --user-temp --days 14` previews; add `--windows-temp`, `--thumbnail-cache`, `--icon-cache`, `--shader-caches`, `--browser-caches`, `--office-caches`, `--delivery-optimization-cache`, `--recycle-bin`, `--error-reports`, `--crash-dumps` or `--windows-minidumps` for those targets, `--json` for structured output, or `--execute` for permanent removal. Delivery Optimization uses only its standard Windows service cache, leaves the service and policy unchanged, and removed content may need to be downloaded again. Recycle Bin cleanup is all-or-nothing across the current Windows shell target. The age setting does not apply, current count and size are rechecked before execution, and a count above the selected limit blocks it. The generic `workflow cleanup` remains diagnostic-only with default settings. Removal tests use substituted providers; native deletion, locked-file behavior and filesystem redirection still require disposable-machine tests. No real cache, report, dump or Recycle Bin items were deleted during development validation.

Native API references: [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) and [FILE_DISPOSITION_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_disposition_info).

### Profile backup verification

The PRUNE profile review excludes loaded, system, current-account and unknown-state profiles before a removal plan can be saved. After running Profiles, select exactly one reviewed profile and expand **Back up and verify a profile**. **Copy and verify** requires a new local NTFS destination that does not exist. It writes durable preparation, repeats the complete profile, dependency, registration and destination checks, requests one bounded copy, then verifies both complete regular-file sets before reporting success. A stopped, failed or uncertain copy preserves its destination and pending evidence. **Create verification files** performs the same source-to-copy comparison for a folder copied separately and creates the fixed receipt and JSON Lines manifest only when they match. **Verify copied backup** checks an existing receipt and manifest. **Check interrupted backup** verifies a pending artifact without copying files again. None of these actions deletes a profile.

`ProfileBackupExecution.RunAsync` is the Engine coordination boundary. `WindowsProfileBackupHost` uses one fixed Robocopy plan that requests data, attributes, timestamps, permissions, ownership, auditing data, directory timestamps and raw encrypted-file copying; excludes junction traversal; copies symbolic links instead of following them; limits retries; and suppresses unbounded file listings. Only Robocopy exit codes 0 through 7 with complete command evidence can proceed to verification. Verification compares every relative path, file length and SHA-256 digest. Missing or extra files, changed contents, traversal, alternate path syntax, duplicate entries, receipt or manifest self-entry, reparse points, malformed or excessive evidence and inconsistent totals are rejected. An uncertain dispatched copy retains a pending record. `ProfileBackupRecovery.TryResolveAsync` only verifies that destination and never repeats the copy.

CLI: `killerbench-cli profiles --select SID --backup-to "X:\NewProfileBackup"` previews one guarded copy. Add `--execute` to request it. The destination must be an absent local NTFS path. `--verify-backup RECEIPT` performs read-only source-to-backup verification, while `--create-backup-artifact DESTINATION` compares a folder copied separately and creates its fixed manifest and receipt. `profiles --recover-backup` verifies an interrupted backup artifact and archives its pending record without retrying the copy. A verified receipt proves that the regular source and destination file sets and contents matched at verification time. Although the copy plan requests Windows security and encrypted-file metadata, the current verifier does not prove ACL, alternate-stream, encrypted-file, application-state or restore behavior. Native profile copying and restoration need disposable-machine validation. Native profile deletion remains unavailable.

### Power options

Select the DEBLOAT review and choose only High performance power, Sleep and display timers, or Hibernation to expose its focused action. High performance activates the existing standard plan. Timer changes require all four AC and battery values, with zero meaning Never. Hibernation disablement removes Windows hibernation support and can also make Fast Startup unavailable. Changed, unavailable or canceled final evidence does the same. Only a command that may have reached Windows retains pending recovery. A dispatched action requires exact verification and preserves its pending record when the result is incomplete. Recovery reads current state and never repeats the original command. ### System servicing

Open **Repairs**, choose DISM component-store repair or SFC system-file repair, read the preview, select **Run this repair on this PC**, then click **GO**. Start KillerBench normally for diagnostics and reviews. Run it as administrator only when executing a repair. Reboot indicators block execution until the machine is restarted and reassessed. Repairs always target the current PC, even when viewing another machine's saved capture. They are manual tools, not automatic recommendations inferred from historical log findings.

DISM runs RestoreHealth and then ScanHealth with automatic restart disabled. KillerBench reads the managed component-repair source policy before selecting RestoreHealth and repeats the complete DISM health and source-policy check at native command dispatch. If DISM reports that the component store cannot be repaired, KillerBench requests review of matching repair media, an in-place repair or a recovery plan and does not offer RestoreHealth. Contradictory DISM outcomes remain Unknown. If Windows Update is blocked and no alternate source is configured, the policy is conflicting or unreadable, or the component-store result changed, RestoreHealth does not start. A configured source preserves eligibility but is not contacted during the check, so access and compatible payloads remain unproven until DISM runs. KillerBench never changes the source policy. SFC runs scannow and then verifyonly, with VerifyOnly repeated immediately before Scannow. If integrity violations are no longer confirmed, Scannow does not start. Stop waits for the current servicing command, up to its one-hour bound, before skipping later steps; closing waits for operation shutdown. A timeout cannot prove Windows stopped servicing or rolled back changes. Failures, restart requirements and unrecognized verification output remain unresolved.

A separate JSON execution journal is created before any command under the user's local application data folder, in KillerBench/Repairs. It records the target, commands, exit codes, bounded output, and verification state. If the final DISM or SFC eligibility check blocks dispatch, the journal records that the repair was skipped and the prepared recovery marker is closed because no mutation started. An interrupted app can leave a journal marked Running; it is not proof of completion. Captures taken before a repair remain historical snapshots. Scan again to collect post-repair evidence. Repairs have no automatic rollback. One repair at a time is allowed across KillerBench processes running as the same user.

CLI preview: `killerbench-cli repair dism` or `killerbench-cli repair sfc`. Adding `--execute` first runs a fresh DISM ScanHealth or SFC VerifyOnly check. The repair runs only when that evidence names the exact requested action; incomplete, clear, unrepairable or mismatched evidence returns for review without dispatch. Ctrl+C requests a stop between commands. Exit codes: 0 for recognized successful verification, 3 for a result requiring review (including ineligible evidence, failed commands or restart required), 1 for preflight/execution errors, 2 for invalid arguments, and 130 for cancellation. Output is retained up to 250,000 characters per stream per step and truncation is recorded.

Repair orchestration is covered by simulated success, denied access, failure, restart-required, cancellation, and verification tests. Native DISM/SFC repair execution still requires hands-on validation in a disposable Windows VM. No repair was executed on the development machine during implementation.

### Windows Update data-store recovery

Use `killerbench-cli update-store-reset` to run a fresh Windows Update search and preview data-store recovery. The reset is offered only when that search returns a recognized structural data-store HRESULT. Add `--execute` only on a disposable test machine or an endpoint with an approved recovery plan. After durable preparation and before stopping a service, KillerBench rereads Installer activity, restart state, administrator access, the exact three service states, the exact store identity and the same structural failure. Any change blocks the reset without running a command. The operation retains the old SoftwareDistribution directory under a unique name, preserves service startup settings and managed update settings, and verifies the result with another search. It does not install updates or restart Windows.

If an operation is interrupted or verification is incomplete, run `killerbench-cli update-store-reset-recover`. Recovery reads the pending record and current Windows state. It never stops services or renames the store again. The retained prior store is not removed automatically. Review it and its disk use before any later manual cleanup.
## Rebuild the Windows Search index

Choose **Windows Search**, check **Rebuild the Windows Search index**, then press **GO**. KillerBench requires administrator access, idle Windows Installer activity, clear supported restart indicators, a running enabled Windows Search service, and the exact non-reparse index directory. It writes a durable preparation record, repeats the servicing, restart, service and directory checks immediately before stopping the service, retains the prior index under a unique sibling name, restarts Windows Search, and verifies the new directory plus the retained copy. Changed, unavailable or canceled final evidence produces a no-change result and closes the prepared guard. Only a stop request that may have reached Windows remains pending.

If an operation is interrupted, the next selected GO reconciles fresh state without repeating the stop, rename, or start commands. The prior index is never deleted automatically. Windows Search policy, indexed locations, service startup mode, and retained data stay unchanged.

The CLI uses `search-index-rebuild` for preview, `search-index-rebuild --execute` for explicit execution, and `search-index-rebuild-recover` for read-only reconciliation.
