# KillerBench landing source

The public site is the flat folder `../bench-landing`, laid out like the other family landing sites: one page per route (`index.html`, `help.html`, `technical.html`, `about.html`, `mcp.html`, `404.html`), `kb.css`, `kb.js`, `kb-i18n.js`, `kb-icon.png`, `favicon.ico`, the shared `family.css`, `feature-carousel.*`, grain images, `brand/`, `screenshots/` and the English-only Engine developer guide in `engine/`. This folder holds what builds it and is never published.

Static pre-release page at https://killerbench.net/. Default: Dark with the family Yellow accent. No public download or release is claimed. Canonical and social URLs use the production domain.

`family.css` is the shared family landing stylesheet. `kb.css` adds only this site's layout and Yellow defaults. Wordmarks use the canonical family SVG generator; regenerate with `python generate-art.py` from this directory (it writes into `../bench-landing`). The generated social image is 1200x630.

Deployed September 12, 2026 to the Cloudflare Pages project `killerbench-landing` (production branch `main`). Publish only the contents of `../bench-landing`. `_headers` defines CSP, HSTS, and other browser security policies.

`license.txt` is a byte-for-byte copy of the root GNU GPLv3 license. Run `python ../check-license.py` to check both copies and the desktop/CLI publish items. Font permission records and required notices are documented in `../LICENSING.md`; final package inventories and public source delivery still need release acceptance. A checked export is not publication approval.

Sources: `templates/index.en.html` and `templates/mcp.en.html` (page markup), `locales/*.json` (one catalog per language for the home, Engine overview and MCP pages), `help/docs/*.md` with translated guides in `help/docs/i18n/<locale>/`, and `engine/docs/*.md`. Edit those, then run `python build-site.py` from this directory. It renders everything with `build-docs.py` and `build-locales.py` in a temporary staging copy (where `build-locales.py --check` and `test-site.py` still run against the per-language output), then flattens the result into `../bench-landing`: English pages carry `data-i18n` keys, every translation goes into `kb-i18n.js`, `kb.js` applies the language chosen in the topbar menu (remembered in localStorage, or `?lang=de` and so on), `docs-search-index.js` holds one search index per language, and `_redirects` sends the old `/<locale>/` routes to `/?lang=<code>`. `python build-site.py --check` checks the public folder alone: every local reference (including links inside translations and search results), all 20 languages, no en or em dashes, no source folders, and the required pre-release statements. Detailed Engine guides remain in English. Run `python check-engine-examples.py` with the .NET 10 SDK and authorized full checkout to compile the two getting-started examples without executing diagnostics. Translation structure is checked automatically; native-speaker review remains a separate acceptance step.

## Prepare and review publication

This work prepares local output only. Do not publish until the reviewed output and package claims have explicit publication approval. No deploy automation is checked into this repository.

1. From this directory, run `python build-site.py` and `python check-engine-examples.py`.
2. Run `python prepare-publish.py C:\path\to\new-empty-output`. Choose a new directory outside the site and its parent directories. The exporter refuses existing output, copies only public HTML/CSS/JS/images/fonts, the canonical `license.txt`, `_headers` and `_redirects`, then checks the exported site again. It never deletes files or publishes.
3. Serve that export on loopback for local review, for example `python -m http.server 8765 --bind 127.0.0.1 --directory C:\path\to\new-empty-output`. Check Home, Help, Technical, About, Engine and MCP at desktop and narrow widths. Use the keyboard for navigation, search and the theme/language menus. Stop the local server when finished.
4. Keep the pending-download message until an official package actually exists. Before changing it, include the confirmed GPLv3 license and resolve compliant Corresponding Source delivery and bundled third-party/font notices; check the Windows x64 package and Desktop Runtime requirement, signature/checksum information and declared repair validation scope.
5. After explicit publication authorization, the site's operator should upload the checked export to the existing Cloudflare Pages project `killerbench-landing`, following that project's current controls. Do not upload source folders or the whole repository. Do not change host, firewall, DNS or Pages security settings as part of this preparation.
6. Verify the resulting live routes and assets, including `/`, `/help`, `/technical`, `/about`, `/engine/`, `/engine/getting-started`, `/mcp`, `/license.txt` and a nonexistent nested path. Check the language menu, a few old `/<locale>/` redirects and documentation search. Record the deployment identity and results. A local check is not a production deployment result.

The top-level `404.html` has absolute asset and navigation paths so missing nested routes do not break its layout. [Cloudflare Pages route matching](https://developers.cloudflare.com/pages/configuration/serving-pages/) documents directory index routes, extensionless HTML redirects and the top-level 404 behavior; including this file prevents Pages' implicit home-page fallback for unknown routes. The simple local Python server verifies files and missing-route status but does not emulate Pages' extensionless redirects or custom 404 rendering.
