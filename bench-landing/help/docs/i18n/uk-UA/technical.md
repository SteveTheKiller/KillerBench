# Технології KillerBench

Погляд під капот: як KillerBench читає комп'ютер із Windows, зберігає чесність даних і вирішує, коли зміна допустима.

## Технологічний стек

KillerBench є власним застосунком Windows. Настільний застосунок, командний рядок і Engine, що лежить в їхній основі, використовують ті самі діагностичні дані та процедури виправлення.

| Компонент | Подробиці |
| --- | --- |
| Інтерфейс | WPF на .NET 10 (`net10.0-windows`), Windows x64, власна рамка вікна |
| Engine | `Engine.Core`, `Engine` і `Engine.Windows`, без посилань на WPF чи елементи керування настільного застосунку |
| Командний рядок | `killerbench-cli`, окремий хост на тому самому Engine |
| Постачальники Windows | .NET, API Windows, PowerShell і засоби командного рядка Windows; кожен працює у фіксованих межах часу, кількості записів і розміру |
| Звіти | Вихідні дані, Зрозумілий звіт, HTML, текст і JSON |
| Довідкові дані | Пакети знань із версіями для кодів помилок, ідентифікаторів обладнання, постачальників і посилань на підтримку |
| Пакування | Інсталятор: залежить від платформи, потребує .NET Desktop Runtime 10 for Windows x64. Портативна версія: автономна, без встановлення середовища виконання |
| Вигляд | 13 тем сімейства та 20 мов |

## Встановлення, папки й дані

KillerBench постачається у двох формах. Інсталятор є стандартним завантаженням і підтримує встановлення для одного користувача або для всіх користувачів. Портативна версія містить власне середовище виконання .NET і працює без встановлення.

KillerBench працює з правами облікового запису, який його запустив. Він не підвищує права самостійно. Запустіть його через **Запуск від імені адміністратора**, коли захищені дані, наприклад засоби захисту BitLocker, чи виправлення потребують прав адміністратора. Підвищення прав ніколи не вибирає й не схвалює виправлення.

### Що робить інсталятор

Інсталятор перевіряє та розпаковує застосунок у `%LOCALAPPDATA%\Programs\KillerBench\` або, після запиту на підвищення прав для всіх користувачів, у `%ProgramFiles%\KillerBench\`. Він додає ярлик у меню «Пуск», необов'язковий ярлик на робочому столі та запис у списку встановлення й видалення програм зі звичайним і тихим видаленням. Портативна версія перевіряє та розпаковує свій вміст у `%LOCALAPPDATA%\KillerBench\Portable\` на час поточного запуску й під час наступного запуску прибирає залишені копії.

### Де що зберігається

| Розташування | Вміст |
| --- | --- |
| `%LOCALAPPDATA%\KillerBench\appearance.json` | Тема, колір акценту, масштаб інтерфейсу й мова |
| `%LOCALAPPDATA%\KillerBench\Workflows\` | Один журнал JSON на кожен запуск процедури: рішення, обмежений вивід команд і результати виправлень |
| `%LOCALAPPDATA%\KillerBench\Repairs\` | Журнали виконання виправлень обслуговування, наприклад DISM і SFC |
| Папки функцій у `%LOCALAPPDATA%\KillerBench\` | Очікувальні записи й результати окремих захищених дій, наприклад `BitLockerBackup`, `Time`, `Firewall` і `Profiles` |
| `%LOCALAPPDATA%\KillerBench\agent-repairs.json` | Рівень виправлень KillerMCP, вибраний у розділі «Про програму» |
| `HKCU` або `HKLM\Software\KillerBench` | Шлях установлення для відповідної області встановлення |
| Вибраний вами файл `.kbench` | Збережений знімок зі збереженими даними |

Нічого не вивантажується. Видаляйте журнал лише тоді, коли дані для невизначеного результату вам більше не потрібні.

## Спершу діагностика

KillerBench розглядає діагностику та зміну як різні завдання. Діагностика лише читає. Зміна відбувається тільки тоді, коли ви вибираєте конкретне виправлення чи дію, переглядаєте її параметри й передумови та підтверджуєте її.

Повна перевірка системи є лише діагностичною, зокрема тоді, коли для вузько спрямованої процедури ввімкнено автоматичне виправлення. Збережені знімки, імпортовані журнали й історичні події ніколи не дають права на виправлення.

### Обмежене збирання

Кожна власна команда й кожен постачальник Windows працюють у фіксованих межах часу, кількості записів і розміру. Постачальник записує код завершення, тайм-аут, обрізання, стандартний вивід і вивід помилок. Невдалий чи обрізаний результат постачальника ніколи не може бути прочитаний як чиста порожня відповідь.

### Мінімальне зберігання

Збирачі зберігають те, що потрібно для висновку. Багато результатів зберігають імена, категорії, кількості, стани й позначки часу, але не зберігають облікових даних, командних рядків, повних шляхів, ідентичностей облікових записів, мережних кінцевих точок і непов'язаних даних подій.

## Дані, які можна простежити

Кожен висновок пов'язаний із даними, що його породили, і звіт завжди відокремлює доведене від лише спостереженого.

| Стан | Значення |
| --- | --- |
| Потребують огляду | Дані підтверджують проблему, яка заслуговує на увагу. |
| Відомості | Дані зібрано й показано для контексту. |
| Незавершені або Невідомо | Перевірка не змогла завершитися або дані були недоступні. Такий результат ніколи не вважається справним. |
| Історичні | Подія з минулого. Вона пояснює історію, але не доводить поточної несправності. |
| Підтверджено | Виправлення чи зміну підтверджено повторним читанням результату. |

### Невідомо теж є результатом

Невідомо означає, що доступ заборонено, джерело відсутнє, постачальник дав збій, вивід має неправильний формат, перевищено межу або дані суперечать одні одним. KillerBench показує це обмеження й наступний корисний крок, а не приховує його.

### Історія залишається історією

Записи подій та імпортовані журнали описують те, що було записано в минулому. Вони можуть вказати на код помилки чи наступну область діагностики. Вони не доводять, що несправність досі активна.

## Захищені виправлення

Виправлення є типізованими операціями з правилами придатності, виконання, перевірки й відновлення. Це не рядки команд, вибрані з рядка журналу. Кожне підтримуване виправлення виконує ту саму послідовність:

1. Зібрати повні поточні дані.
2. Зіставити один підтримуваний рецепт.
3. Переглянути обов'язкові параметри й наслідки.
4. Підтвердити адміністративні передумови й передумови політики.
5. Повторно зібрати вирішальні дані безпосередньо перед зміною.
6. Записати стійкий запис підготовки.
7. Виконати одну обмежену власну дію.
8. Зібрати свіжі дані перевірки.
9. Записати результат: підтверджено, заблоковано, зупинено чи невизначено.

Якщо вирішальні дані змінюються до виконання дії, KillerBench зупиняється, не виконуючи її.

### Явний вибір

Виправлення, що залежать від параметра, потребують від вас точного вибору, наприклад тому, черги принтера, місця для резервної копії ключа відновлення, значення живлення, версії пакета чи джерела виправлення. KillerBench ніколи не вигадує цих значень.

### Керовані комп'ютери

Групова політика й системи керування пристроями можуть зробити локальну зміну неефективною чи недоречною. Підтримувані виправлення перевіряють, кому належить параметр, і зупиняються, коли власник керований або невідомий. Параметри, що належать політиці, не змінюються.

### Автоматичне виправлення

Автоматичне виправлення лише дає змогу продовжити придатним рецептам. Воно не обходить даних, не вибирає відсутніх параметрів, не ігнорує політики, не повторює невизначеної дії, не перезапускає Windows і не перетворює висновок, що потребує огляду, на виправлення.

## Журнали й переривання

Перш ніж KillerBench попросить Windows внести зміну, він записує, що збирається зробити. Кожну зміну збережено в журналі в `%LOCALAPPDATA%\KillerBench`.

Після зміни KillerBench повторно читає результат і повідомляє **Підтверджено** лише тоді, коли Windows показує очікуваний стан. Якщо Windows повідомляє про успіх, але стан не змінився, результат так і каже, і нічого не повторюється.

Процес може зупинитися після того, як Windows отримала запит, але до завершення перевірки. Очікувальний запис залишається, а пізніше узгодження читає свіжий стан, щоб з'ясувати, що сталося. Узгодження не є автоматичним відкатом і ніколи не повторює початкову зміну. Зберігайте журнал, коли результат невизначений.

## Чого він не робитиме

- Очищати TPM, видаляти засоби захисту, яких він не створював, чи показувати паролі відновлення.
- Змінювати параметр, яким керує групова політика чи система керування пристроями.
- Запускати виправлення лише тому, що історична подія чи імпортований звіт згадує проблему.
- Перетворювати відсутні, часткові чи невдалі дані на висновок про справність.

## Звіти

Кожен запуск створює звіт, який можна читати, фільтрувати й експортувати. Звіт розділяє:

1. Що перевірено
2. Яку проблему знайдено
3. Які дані підтверджують висновок
4. Яку дію запропоновано чи виконано
5. Як перевірено результат
6. Що залишається невідомим або потребує перезапуску

**Вихідні дані** зберігають технічні дані з початковими номерами рядків, щоб будь-який висновок можна було простежити до джерела. **Зрозумілий звіт** підсумовує той самий запуск простою мовою, починаючи з наступного безпечного кроку. HTML-звіти використовують систему тем Killer Tools і залишаються читабельними без застосунку. Текст зручний для перенесення, а JSON зберігає структуровані поля для іншої програми.

## Збережені журнали й знімки

KillerBench може досліджувати дані, нічого не запускаючи на комп'ютері. Перетягніть текстовий журнал у вікно або вставте шлях до нього й виберіть **Відкрити журнал**. Рядки CBS, CSI і Setup розбираються з їхніми позначками часу, а висновки посилаються на точний початковий рядок. Файли EVTX і XML подій можна імпортувати так само.

**Сканувати Windows Update** виконує на вимогу збирання лише для читання журналів CBS, DISM, Panther і відкату Setup, каналів подій оновлень і обслуговування, станів служб оновлень, вільного місця, часу роботи, ознак очікуваного перезавантаження й вибраної політики оновлень. **Зберегти знімок** записує збережені дані у файл `.kbench`. **Відкрити знімок** знову відкриває його без початкових файлів і повторно оцінює за встановленими правилами, тож ті самі правила дають ті самі висновки.

## Демонстраційний режим

Запустіть `KillerBench.exe --demo`, щоб спробувати **Запустити діагностику** на вигаданій робочій станції. Кожна процедура створює синтетичні дані та розраховану в часі індикацію перебігу. Жоден постачальник Windows не викликається, жодна команда виправлення не виконується, і жоден журнал не записується. Окремі кнопки інструментів поза **Запустити діагностику** залишаються робочими, тому не використовуйте їх як демонстраційні дії.

`KillerBench.exe --demo-screenshot` відкриває звіт повної перевірки системи лише для перегляду для фіксованого вигаданого комп'ютера. Клацання в робочій області, сполучення клавіш і перетягування файлів заблоковано.

## Пакети знань

Великі довідкові дані, що часто оновлюються, зберігаються в пакетах знань, а не в діагностичній логіці: коди помилок Windows і Setup, ідентифікатори постачальників і пристроїв, довідники PCI, USB, ACPI і UEFI, дані про постачальників мережних OUI, розташування драйверів і підтримки, а також добрані посилання на підтримку.

Кожен пакет указує свій формат, версію схеми, джерело, ревізію джерела, час створення й хеш вмісту, і KillerBench перевіряє їх перед використанням. Невідомий чи недійсний пакет залишається недоступним, а не підміняється здогадкою. Оновлення завантажується в тимчасове розташування, перевіряється, а потім замінює активний пакет за один крок, тож невдале оновлення залишає попередній пакет на місці.

Дані знань можуть пояснити ідентифікатор чи підказати, де шукати далі. Вони не можуть перетворити історичний код на поточну несправність, автоматично вибрати драйвер чи дати право на виправлення.

## Оновлення й підписування

Під час запуску KillerBench запитує в GitHub останній стабільний випуск з обмеженням у чотири секунди й пропонує оновлення лише тоді, коли цей випуск новіший. Перевірку можна вимкнути параметром **Перевіряти оновлення під час запуску** в розділі «Про програму» або в запиті на оновлення. Завантажується пакет, що відповідає запущеній копії, інсталятор чи портативна версія, і його SHA-256 має збігатися з файлом `SHA256SUMS.txt` випуску, перш ніж щось буде встановлено. Застосунок закривається й знову відкривається, щоб завершити оновлення. Фонової служби немає.

Картка «Про програму» показує версію, видавця й відбиток сертифіката підписування коду, а також SHA-256 запущеного виконуваного файлу, щоб ви могли перевірити свою копію.

## KillerMCP

KillerBench не містить агента ШІ. [KillerMCP](../mcp.html) може підключити агента до того самого Engine. **Параметри KillerMCP** у розділі «Про програму» визначають, що цьому агенту дозволено:

| Параметр | Дія |
| --- | --- |
| Вимкнено (за замовчуванням) | Агент не може запитати виправлення. |
| Дозволити KillerMCP виконувати безпечні виправлення | Агент може запитувати виправлення, класифіковані як безпечні. |
| Дозволити також виправлення, що переривають роботу | Стають доступними виправлення, що переривають роботу, і кожне з них усе одно потребує схвалення. |

Підвищити рівень може лише людина за цим комп'ютером. Після невизначеного результату виправлення KillerMCP записує блокування, і виправлення від агента залишаються заблокованими, доки хтось не зніме його в розділі «Про програму».

## Локалізація

Інтерфейс доступний 20 мовами: англійською, бенгальською, чеською, німецькою, іспанською, французькою, угорською, італійською, японською, казахською, норвезькою, польською, португальською (Бразилія), російською, словенською, турецькою, українською, в'єтнамською, а також спрощеною й традиційною китайською. Зміна мови застосовується одразу, зокрема до назв розділів і процедур, вітального тексту й відкритого зрозумілого звіту. Відсутній текст відображається англійською.

Дані, висновки Engine, журнали й вихідні дані залишаються англійською, як і журнал Windows, тож звіт однаково читається на будь-якому комп'ютері, і в ньому можна шукати точний текст.

## Командний рядок і коди завершення

`killerbench-cli` запускає той самий Engine без настільного застосунку. Перебіг виводиться в стандартний потік помилок, а JSON у стандартний вивід. Більшість команд за замовчуванням показують попередній перегляд, а для зміни потрібен `--execute`. Відповідні команди `-recover` переглядають перервану дію, не повторюючи її. Див. [Запуск KillerBench зі скриптів](use-the-cli.html) і [довідник команд](cli.html).

| Код завершення | Команди процедур | Сканування й відкриття |
| --- | --- | --- |
| 0 | Немає нерозв'язаних проблем у перевірених областях | Охоплення завершено |
| 1 | Помилка запуску чи журналу | Збій |
| 2 | Неприпустимі аргументи | Неприпустимі аргументи |
| 3 | Потрібна увага | Часткове збирання |
| 4 | Перед перевіркою потрібен перезапуск | |
| 130 | Зупинено | Скасовано або вичерпано загальний тайм-аут |

Жоден код завершення не засвідчує, що комп'ютер справний.

## Архітектура

Engine розділено на три проєкти без інтерфейсу. `Engine.Core` надає примітиви й декларативні рецепти, `Engine` відповідає за спільні процедури й дані, а `Engine.Windows` реєструє власних постачальників. Настільний застосунок, CLI і тести є окремими хостами.

| Рівень | Відповідальність |
| --- | --- |
| Збирачі можливостей | Читають обмежений стан Windows для однієї точної області |
| Аналізатори даних | Перевіряють форму, ідентичність, повноту й межі |
| Діагностичне тлумачення | Перетворює дані на явні стани процедур |
| Оркестрування процедур | Поєднує перевірки, перебіг, рецепти й журнали |
| Координатори виправлень | Повторно перевіряють придатність, готують, змінюють, перевіряють і узгоджують |
| Звіти | Показують проблеми, дії, результати й обмеження |
| Пакети знань | Надають довідкові дані з версіями без зміни логіки |

Збирачі блокуються за невизначеності, коли ідентичність неоднозначна, вивід має неправильний формат, перевищено межу чи неможливо перевірити потрібні повноваження. Engine сьогодні орієнтований на Windows і не є кросплатформним. [Посібник розробника Engine](../engine/index.html) описує API, CLI і вбудовування Engine в інший хост .NET.

## Конфіденційність і мережа

Діагностика й аналіз журналів виконуються локально, без служби ШІ та облікового запису KillerBench. Журнали й збережені дані залишаються в папках `%LOCALAPPDATA%\KillerBench` локального облікового запису.

Вибрані вами дії можуть звертатися до свого місця призначення, наприклад Windows Update, служб завантаження програм чи резервного копіювання ключа відновлення в Active Directory або Entra ID. Перевірка оновлень під час запуску звертається до GitHub, а оновлення знань та інсталятор KillerMCP звертаються до своїх налаштованих служб. Клієнт ШІ, що використовує [KillerMCP](../mcp.html), може отримати довідковий результат, який він запитав.

Необроблені журнали, імпортовані файли й експортовані дані можуть містити імена комп'ютерів, облікові записи, шляхи чи конфіденційний вихідний текст. Переглядайте їх, перш ніж ділитися, і ніколи не включайте ключі відновлення, облікові дані чи дані клієнтів до публічного звіту.

## Стан розробки

KillerBench перебуває в розробці, і загальнодоступного завантаження ще немає. Охоплення виправлень досі розширюється, а перевірка власних виправлень триває. Успішна збірка чи змодельована перевірка не встановлюють поведінки власного виправлення. Одноразові віртуальні машини Windows використовуються для перевірки кожної власної зміни в різних версіях Windows і станах збою. Повну модель безпеки описано на сторінці [Як зміни залишаються безпечними](safety.html).

## Глосарій

Прості визначення термінів, що використовуються на цій сторінці, в алфавітному порядку.

| Термін | Значення |
| --- | --- |
| BITS | Фонова інтелектуальна служба передавання, служба Windows, яка завантажує оновлення та інші файли у фоновому режимі. |
| CBS | Component-Based Servicing, підсистема Windows, що встановлює оновлення й компоненти. Її журнал: `CBS.log`. |
| DISM | Deployment Image Servicing and Management, засіб Windows, який перевіряє та виправляє сховище компонентів. |
| Panther | Папка, у яку програма встановлення Windows записує журнали оновлення. |
| SFC | System File Checker, засіб Windows, який перевіряє та відновлює захищені системні файли. |
| TPM | Trusted Platform Module, мікросхема безпеки, яку BitLocker використовує для захисту ключа диска. |
| Блокування за невизначеності | Коли дані неоднозначні, відсутні чи завеликі, результатом буде «Невідомо», і жодні зміни не допускаються. |
| Власник політики | Групова політика чи система керування пристроями, яка керує параметром. KillerBench не змінює таких параметрів. |
| Дані | Те, що KillerBench фактично прочитав із Windows, збережене разом із джерелом, щоб висновок можна було простежити. |
| Журнал | Локальний запис JSON, створений перед зміною й оновлений після неї, щоб перервану дію можна було згодом переглянути. |
| Знімок | Збережений файл `.kbench` зі збереженими даними, який можна знову переглянути без початкового комп'ютера. |
| Очікувальний запис | Запис, що позначає зміну як можливо надіслану до Windows. Він блокує повтор, доки узгодження не прочитає результат. |
| Пакет знань | Перевірений файл довідкових даних із версією, наприклад кодів помилок чи ідентифікаторів обладнання. |
| Підвищення прав | Робота з правами адміністратора після запиту Windows. KillerBench ніколи не підвищує права самостійно. |
| Підтверджено | Результат прочитано з Windows, і він збігся з тим, чого мала досягти зміна. |
| Процедура | Один запуск інструмента: перевірки, які він збирає, рецепти, які він може використати, і звіт, який він створює. |
| Рецепт | Типізоване виправлення з власними правилами придатності, виконання, перевірки й відновлення. |
| Узгодження | Читання свіжого стану після переривання, щоб дізнатися, що сталося, без повтору зміни. |
