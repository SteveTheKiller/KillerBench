从这里开始

KillerBench 是面向技术人员的 Windows 诊断和修复工作台。它会先检查计算机，并用每项结论背后的证据解释所发现的问题；只有在你选择具体的修复并确认后，才会更改 Windows。

KillerBench 正在开发中，目前还没有公开下载。这些页面介绍的是当前版本。

功能

  • 对 Windows 更新、设备、存储、网络、打印、安全、应用和配置文件运行只读诊断，然后生成可读报告。
  • 提供受保护的修复，仅在新证据准确证明问题时才运行，并在之后验证结果。
  • 涵盖 BitLocker、隐私设置、Windows 精简和新计算机准备等设置与加固工作。
  • 诊断和报告分析在本地运行，无需 AI 或 KillerBench 账户。所选操作（例如下载和将恢复密钥备份到 Entra ID）可能会连接外部服务。
  • 控制台、报告、确认框以及“打开”“保存”和“文件夹”对话框都使用应用的当前主题。

Windows 和运行时

  • 当前的发布目标是 Windows x64。Windows 11 x64 是当前实机验证的基准。不提供原生 ARM64、x86 和 Windows Server 发行版。
  • KillerBench 有两种打包方式。安装程序 依赖框架，需要 .NET Desktop Runtime 10 for Windows x64。普通的 .NET Runtime、ASP.NET Core Runtime 和 .NET Framework 不提供 WPF。便携版自带运行时，无需单独安装。命令行工具 killerbench-cli.exe 需要 .NET 10 Runtime for Windows x64。SDK 仅用于开发，日常使用不需要。
  • 请使用 .NET 10 on Windows 支持的 Windows 版本。运行时受支持并不表示 KillerBench 的修复已在每个受支持的版本或内部版本上经过验证。Windows 10 的支持仍待定，其受支持的版本受 Microsoft 当前生命周期要求的限制。
  • 请仅从 Microsoft 的 .NET 10 下载页面 获取 Desktop Runtime，并选择 .NET Desktop Runtime、Windows、x64。请遵守所在组织的软件安装规定。

如果 dotnet 可用，dotnet --list-runtimes 应列出 x64 安装的 Microsoft.WindowsDesktop.App 10.0.x。仅为其他体系结构安装的运行时不满足 x64 安装程序软件包的要求。

软件包发布后

  1. 请使用本网站链接的官方下载。目前还没有可用的 KillerBench 下载链接。
  2. 阅读该软件包的要求、GPLv3 许可证、对应源代码的获取说明、随附的第三方声明以及签名和校验和信息。仅凭文件名无法证明真实性。
  3. 为当前账户运行安装程序，或在提升权限提示后为所有用户运行安装程序。它会添加开始菜单快捷方式、可选的桌面快捷方式以及“添加或删除程序”条目。便携版无需安装即可运行。
  4. 以普通账户启动 KillerBench，并按照 首次诊断 操作。诊断时的访问失败会保持可见；提升权限是另一项有意的选择。

不要为了运行未经验证的副本而绕过 Windows 安全警告。在选择任何会更改计算机的操作之前，请保留最新的备份。

启动时，KillerBench 会在 GitHub 上检查是否有更新的稳定版本，并在安装前征求你的同意。下载内容必须与公布的 SHA-256 校验和匹配。可以在“关于”中通过 启动时检查更新 关闭此检查。

当前限制

当前版本包含十二个分区、只读诊断、报告以及单独选择的修复功能。实机修复验证仍在进行中。界面能够运行、生成成功或测试数据的结果都不能证明在真实计算机上的修复行为。请参阅 如何保证更改安全。

产品首页上的示意控制台是合成输出。应用的最终截图和首个公开软件包仍在准备中。

源代码、许可证和支持

KillerBench 采用 GPLv3 许可证。首个公开软件包的源代码提供说明和第三方字体许可仍待定。有关源代码可用性、分发声明、证据隐私和支持信息，请阅读 关于 KillerBench。Engine 指南 面向拥有授权源代码检出的开发人员，并不表示已有公开的 Engine 软件包。

先阅读 下载和设置，然后运行完整系统扫描。扫描会收集诊断证据并保存本地日志，但不会运行修复。结论描述的是所检查的范围，而不是计算机上所有可能的故障。

运行扫描

  1. 打开 KillerBench。诊断 分区会打开，并已选中 完整系统扫描。
  2. 首次运行时，请保持 自动修复已确认的问题 处于关闭状态。
  3. 按 运行诊断。每项检查运行时，右侧的 原始输出 中会显示进度。
  4. 完成后，输出窗格会切换到 可读报告。

请先以非提升权限启动。部分 Windows 证据（例如 BitLocker 保护器和受保护的服务）需要管理员权限。在标准账户下，这些检查会报告证据不可用。如果需要这些证据，请先完成当前运行并保留报告，然后有意地通过 以管理员身份运行 重新打开 KillerBench。提升权限不会选择或批准任何修复。

阅读报告

报告开头会显示 需要审阅、已验证的修复、未完成 和 已检查 的数量，然后是建议的下一步。

  • 需要注意的问题 按重要性列出证据所支持的问题。
  • 收集的信息 显示已读取的内容，包括不完整或不可用的证据。
  • 过去的事件会标记为历史记录。上个月的错误不会被视为当前故障。

缺失的证据永远不会被视为正常。如果某项检查无法运行，报告会明确说明。

自行选择检查

打开 选择检查（高级） 可以选择单项检查，而不是运行完整扫描。应用中的每个分区还有专门的工具，本指南的 分区 页面对此有介绍。

修复发现的问题

当报告建议修复时，会指明要打开的分区和工具。首次修复前，请阅读 如何保证更改安全。实机验证仍在进行中；诊断成功并不表示所提供的每项修复都已在你的 Windows 版本上经过测试。在进行任何更改之前，请保留备份，并仔细查看确切的目标和后果。

KillerBench 窗口有三个窗格，与你的工作方式一致：在左侧选择分区，在中间设置工具选项，在右侧阅读输出。选项下方可以打开活动日志。

分区

左侧边栏将所有工具分为十二个分区：诊断、修复、更新、设备、网络、应用、维护、机器准备、安全、BitLocker、隐私和存储。拖动其边缘可以调整大小，拖过最小宽度则会将其收起。

工具选项

中间窗格显示所选分区、其工具列表以及所选工具的选项。可能更改计算机的选项默认始终处于关闭状态。按 运行诊断 启动工具。开启 自动修复已确认的问题 后，同一按钮会显示为 运行修复。停止 会在当前命令完成后结束运行。

输出

右侧的输出窗格有两种视图。

  • 原始输出 在收集过程中显示技术证据及其原始行号。工具运行时它会自动打开。
  • 可读报告 显示上一次运行的完整报告。运行结束后，它会替换原始输出。

使用原始输出中的筛选框可以只显示匹配的行。导出报告 会将报告连同其来源路径和证据摘录一起保存。会话来源 列出本次会话中收集的所有证据。

活动日志

工具选项下方的活动日志记录 KillerBench 在本次会话中执行的操作。

主题、语言和快捷键

侧边栏与工具选项之间的导轨上有主题选择器、语言选择器、快捷键列表和活动日志开关。KillerBench 提供 13 种主题和 20 种语言。

烟熏玻璃风格的控制台和可读报告会跟随当前主题。确认框以及“打开”“保存”和“文件夹”对话框使用相同的系列样式，包括 98SE 主题。请在打开对话框之前选择主题，以便在整个工作流程中使用该外观。

KillerBench 将诊断和更改视为两项不同的工作。诊断只读取。完整系统扫描从不运行修复。请选择具体的修复或操作，查看其选项和前提条件，然后确认建议的更改。

更改之前

  1. 新证据。 工具会重新读取当前状态。已保存的报告或旧事件永远不能授权更改。
  2. 确切的适用条件。 只有当证据与更改所修复的问题完全匹配时，才会提供该更改。任何不完整的情况都会阻止更改。
  3. 你的确认。 在确认对话框中查看所选操作。某些操作（例如解密驱动器）需要第二次确认。对话框跟随应用的当前主题，其外观不会改变操作的要求。
  4. 前提条件。 会检查管理员权限、重启状态以及策略或设备管理对设置的所有权。由策略拥有的设置保持不变。
  5. 待处理记录。 KillerBench 会在请求 Windows 执行操作之前，先记录即将执行的内容。
  6. 最后复查。 在发出请求前会立即再次检查所有内容，因此期间发生的变化会让操作停止。

更改之后

  • KillerBench 会读回结果，只有当 Windows 显示预期状态时才报告 已验证。
  • 如果 Windows 返回成功但状态没有变化，结果会如实说明，并且不会重复任何操作。
  • 每项更改都保存在 %LOCALAPPDATA%\KillerBench 下的日志中。

如果操作被中断

当请求可能已到达 Windows 但验证尚未完成时，受支持的记录日志的操作会保留待处理记录。请使用该操作文档中说明的核对方式或相应的 -recover 命令来检查该记录。核对不是自动回滚。结果不确定时请保留日志，不要手动重复更改。崩溃、取消和下次启动时的行为仍需针对每项操作进行实机验证。

KillerBench 不会做的事

  • 清除 TPM、删除不是由它创建的保护器，或显示恢复密码。
  • 更改由组策略或设备管理控制的设置。
  • 仅因为历史事件或导入的报告提到了某个问题就运行修复。

诊断和报告分析在本地运行。你选择的操作可能会连接外部目标，包括软件下载或将恢复密钥备份到 Active Directory 或 Entra ID。确认之前请检查目标。已保存的捕获和原始证据可能包含计算机标识和来源路径，因此共享前请先检查。

开发状态

修复范围仍在扩展。生成成功或模拟检查并不能证明实机修复的行为。仓库中的 VM-VALIDATION.md 记录了在一次性 Windows 计算机上的场景以及剩余的验证工作。

操作指南

当更新失败、停滞或反复重新安装时使用本指南。KillerBench 会先读取更新链，用其背后的证据解释故障，并且只有在新证据准确证明该问题时，才会启动服务或修复组件存储。

开始之前

  • 以管理员身份运行 KillerBench。更新服务、组件存储和受保护的系统文件需要提升权限才能获得完整证据。
  • 如果 Windows 已有待处理的重启，请先重启。在重启状态清除之前，许多更新修复都会被阻止。
  • 执行维护工作时，请让计算机连接交流电源。

找出更新失败的原因

  1. 打开 更新，并在工具列表中选择 Windows 更新。
  2. 第一次运行时保持 自动修复已确认的问题 关闭，然后按 运行诊断。
  3. 阅读 可读报告。它会列出已停止的更新服务、待处理的重启、可用空间不足、组件存储损坏以及 Windows 记录的确切错误代码，并给出建议的下一步。
  4. 如果报告中出现错误代码，相应的后续检查会自动运行。你也可以使用 killerbench-cli update-code 0x80070002 自行查询。

监视看似停滞的更新

在 更新 中选择 维护活动监视器，然后按 运行诊断。它会反复拍摄更新、Setup 和 Installer 活动、传输总量以及重启指示的快照。活动仅作为证据显示，它本身绝不会断定存在停滞或故障。

修复报告发现的问题

  1. 开启 自动修复已确认的问题，再次运行 Windows 更新。它可以启动已确认停止的已启用更新服务，并且仅在实时检查确认损坏时才运行 DISM 或 SFC。
  2. 对于单个服务，请改用其专用工具，例如 BITS 服务、加密服务、Windows 模块安装程序 或 更新协调器服务。每个工具只针对该服务提供恢复。
  3. 当报告要求重启时，请先重启，再运行其他任何内容。KillerBench 会记录需要重启的结果，并将后续工作推迟到重启完成之后。

每项修复都会记录到日志中并读回。完整流程请参阅 如何保证更改安全。

安装特定更新

  1. 在 更新 中选择 可用更新，然后按 运行诊断，从已配置的来源查找更新。
  2. 选择所需的更新，然后按 预览所选内容。预览会准确列出将要安装的内容以及是否需要重启。
  3. 请在阅读预览后再安装。KillerBench 绝不会替你选择或批准更新。

通过命令行

killerbench-cli update-search
killerbench-cli update-history
killerbench-cli servicing-monitor --samples 10
killerbench-cli update-plan --select GUID:REVISION --execute

请参阅 update-search、update-history、servicing-monitor 和 update-plan。如果安装被中断，请运行 update-recover；它会检查结果，并且绝不会重试更新。

当 Windows 组件损坏时使用本指南，例如功能无法安装、更新报告组件错误或系统工具崩溃。KillerBench 只有在实时检查确认损坏后才运行 DISM 和 SFC，然后验证结果。

开始之前

  • 以管理员身份运行 KillerBench。
  • 先完成所有待处理的重启。
  • 如果计算机受管理，请检查策略是否将 DISM 指向特定的修复来源。KillerBench 会报告该策略，但不会更改它。

检查损坏

  1. 打开 修复，然后选择 系统文件。
  2. 保持 自动修复已确认的问题 关闭，然后按 运行诊断。
  3. 阅读报告。它会清点维护包、可选功能和功能的状态，检查前提条件，并扫描受保护的系统文件。结果正常则表示不提供修复。

修复已确认的损坏

  1. 开启 自动修复已确认的问题，然后按 运行修复。只有当实时检查确认损坏时，KillerBench 才会选择 DISM 或 SFC。
  2. 等待验证。只有当后续检查读回已修复的状态时，报告才会显示 已验证。
  3. 如果报告指出存储无法恢复或修复来源不可用，请就此停止。重复修复不会改变结果。

中断的 DISM 或 SFC 运行会在下次启动时进行核对，而不会重复维护命令。

清理组件存储

在 更新 中选择 组件存储清理。它会先询问 Windows 是否建议清理。可选的维护会删除被取代的组件并再次分析。它绝不会使用 ResetBase，也绝不会手动删除 WinSxS 内容。

通过命令行

killerbench-cli component-repair-source
killerbench-cli repair dism
killerbench-cli repair sfc --execute
killerbench-cli servicing-logs

请参阅 component-repair-source、repair 和 servicing-logs。repair 默认只显示预览，仅在使用 --execute 时才会执行。

查看剩余空间

预览清理

  1. 打开 维护，然后选择 清理。
  2. 勾选所需的目标，例如 当前用户临时文件、Windows 临时文件、当前用户浏览器缓存、传递优化缓存 或 当前用户回收站。将指针悬停在目标上可以准确查看其涵盖的文件夹。
  3. 设置 最小天数 和 每个目标的最大文件数。
  4. 在 在重新检查后执行所选的永久清理 关闭的情况下按 运行诊断。报告会列出每个目标的候选文件和预计空间。不会删除任何内容。

删除文件

  1. 开启 在重新检查后执行所选的永久清理，然后按 运行诊断。
  2. KillerBench 会在删除前重新检查每个候选文件，跳过最近的、受保护的或正在使用的文件，并将每个结果记录到日志中。

永久清理会绕过回收站，且无法撤消。删除错误报告和崩溃转储会丢弃你调查崩溃时可能需要的证据，因此请先检查这些内容。

检查卷

  1. 打开 存储，然后选择 存储。
  2. 在 要检查的卷 中选择驱动器，然后按 运行诊断。

当计算机无法上网、无法访问服务器或名称，或者连接频繁断开时使用本指南。KillerBench 会依次检查适配器、地址、网关、DNS 和防火墙，并且只有在新证据证明确有必要时，才会续订租约或启动服务。

检查连接

  1. 打开 网络，然后选择 网络。
  2. 要测试特定目标，请填写 主机名查找（可选），或者 TCP 目标（可选） 和 TCP 端口。若只检查本地配置，请留空。不会发送任何应用程序数据。
  3. 如果网络较慢，请设置 每次查找或连接的超时（秒）。
  4. 保持 自动修复已确认的问题 关闭，然后按 运行诊断。
  5. 阅读报告。它会区分缺少地址、缺少网关或网关不可访问、DNS 配置问题、代理设置、防火墙配置文件不匹配以及查找或连接失败，并为每种情况给出下一步。

网关有响应并不能证明可以访问 Internet；通过已配置的解析程序查找失败，也不代表该网站已停止运行。

修复报告发现的问题

  1. 开启 自动修复已确认的问题，再次运行 网络。它可以启动已启用的 DNS Client、DHCP Client、SMB 客户端、Network Location Awareness、Network List 和 IP Helper 服务，并为缺少可用 IPv4 地址的已连接物理 DHCP 适配器续订租约。
  2. 续订期间连接可能会短暂断开。静态地址和虚拟适配器永远不会被更改。
  3. 对于缓存中某个错误的名称，请使用针对该确切主机的 DNS 缓存刷新，而不是清除所有内容。

路由、Hosts 条目、DNS 服务器、防火墙规则、Winsock 提供程序和网络配置文件始终保持不变。

无线、有线登录和代理

  • 无线网络 会检查适配器和 WLAN AutoConfig，并在服务停止时启动它。
  • 有线身份验证 (802.1X) 会针对需要在端口登录的网络，对 Wired AutoConfig 执行相同的操作。
  • WinHTTP 自动代理 会显示计算机和当前账户已保存的代理设置。KillerBench 在诊断期间绝不会获取 PAC URL 或更改代理设置。

通过命令行

killerbench-cli workflow network --host example.com --tcp example.com 443
killerbench-cli dns-check example.com --timeout-seconds 5
killerbench-cli tcp-check fileserver 445
killerbench-cli dhcp-renew
killerbench-cli dns-cache example.com --execute

请参阅 workflow、dns-check、tcp-check、dhcp-renew 和 dns-cache。

使用本指南可以启用 BitLocker、备份恢复密钥并确认驱动器已受保护。KillerBench 会在开始加密之前备份并验证恢复密码，并且绝不会显示或记录恢复密码。

开始之前

  • 以管理员身份运行 KillerBench。
  • Windows 驱动器需要 TPM 保护器和恢复密码保护器。数据驱动器只需要恢复密码。
  • 确定恢复密钥备份的保存位置：位于要加密的驱动器之外的文件，以及可选的 Active Directory 或 Microsoft Entra ID。

  1. 打开 BitLocker，然后在 卷 中选择驱动器。
  2. 将操作保持为 检查，然后按 运行诊断。报告会显示加密状态、保护状态和保护器标识。
  3. 如果 TPM 存在但尚未就绪，请先在 安全 中准备它。KillerBench 绝不会清除 TPM。

添加所需的保护器

  1. 打开 更多 BitLocker 操作。
  2. 选择 添加 TPM 保护器 或 添加恢复密码，按 预览，勾选 按下“运行操作”时对所选驱动器进行此更改，然后按 运行操作。
  3. 立即备份新的恢复密码。KillerBench 不会显示它。

备份恢复密钥并加密

  1. 按 查找恢复保护器，然后选择恢复密码保护器。
  2. 输入位于要加密的驱动器之外的备份文件的完整路径。
  3. 选择 加密，选择加密方法，然后勾选 在我选择“运行诊断”时备份所选的恢复密钥，然后开始加密。
  4. 按 运行诊断。KillerBench 会写入备份、验证备份，然后开始一次加密。
  5. 加密会在后台继续进行。稍后运行 检查，确认驱动器报告已完全加密且保护已开启。

备份到 Active Directory 或 Entra ID

在 更多 BitLocker 操作 中，为所选保护器选择目录备份。KillerBench 会报告 Windows 已接受请求，但无法读取目录中的副本，因此请在 Active Directory 或 Entra 管理中心中确认。

数据驱动器和自动解锁

数据驱动器加密后，启用自动解锁 可以让它在 Windows 启动时解锁。Windows 驱动器必须已完全加密且保护已开启。

通过命令行

killerbench-cli bitlocker-protector-add C: recovery --execute
killerbench-cli bitlocker-encrypt C: RECOVERY_PROTECTOR_GUID D:\Keys\C-recovery.txt --execute
killerbench-cli bitlocker-escrow C: RECOVERY_PROTECTOR_GUID entra --execute

请参阅 bitlocker-protectors、bitlocker-protector-add、bitlocker-encrypt 和 bitlocker-escrow。每个命令都有对应的 -recover 命令，用于处理中断的请求。

当 Windows 意外重启、显示停止错误或某个应用程序反复崩溃时使用本指南。KillerBench 会将崩溃、关机、硬件错误和可靠性证据汇总到一份报告中。它只描述记录的内容，绝不猜测根本原因。

检查计算机

  1. 打开 诊断，然后选择 关键指标。
  2. 按 运行诊断。报告会汇总内存、磁盘运行状况、设备问题、可靠性监视器历史记录、硬件错误记录、崩溃报告、意外关机和 Windows 内存诊断结果。

  • 硬件错误历史记录 会结合设备问题和磁盘运行状况，读取 WHEA 和内存诊断记录。

KillerBench 会列出转储配置和转储文件的元数据，并可以分析小型转储的结构，以获取异常和模块名称。桌面应用中绝不会打开转储内容。加载错误检查知识包后，停止代码会解析为其文档中说明的含义。

当你需要在脚本、RMM 作业或远程控制台中获取 KillerBench 证据时，请使用命令行。killerbench-cli 运行与桌面应用相同的 Engine，并输出 JSON。

入门

  1. 在 killerbench-cli.exe 所在位置打开 PowerShell，或将其文件夹添加到路径中。
  2. 运行 killerbench-cli help，列出所有命令及其安全边界。
  3. 运行 killerbench-cli diagnostic-scopes，查看 11 个建议的诊断组。

运行扫描并保存报告

killerbench-cli full-scan --report C:\Reports\scan.html --json

除非添加 --auto-repair，否则 full-scan 是只读的。--report 会写入与应用导出的相同主题样式报告。使用 --scope 可以只检查部分区域，使用 common-check 可以在没有工作流程日志的情况下获取合并的 JSON。

了解退出代码

代码含义
0预览或已验证的结果成功。
1启动、输入或日志错误导致命令停止。
2无法识别参数。
3被阻止、失败或未验证。
4工作流程需要先重启才能验证。
130你停止了它。

只读命令的退出代码 0 表示命令已运行，而不是计算机运行正常。请阅读 JSON 了解结论。

进行更改

所有可能更改计算机的命令默认都只显示预览。请阅读预览，然后使用 --execute 运行同一命令。如果请求被中断，请运行相应的 -recover 命令；它会报告实际结果，并且绝不会重复更改。

killerbench-cli dhcp-renew
killerbench-cli dhcp-renew --execute
killerbench-cli dhcp-renew-recover

重新打开以前的结果

killerbench-cli workflow-journal C:\Users\me\AppData\Local\KillerBench\journal.json
killerbench-cli workflow-report journal.json report.html --include-repairs

完整系统扫描

检查 49 个诊断区域，然后将每个已安装的服务恢复方案与维护、DHCP、打印、Defender、时间和 WMI 方案一起评估。检查可能需要几分钟。自动修复是可选的，需要每个方案自己的当前证据、计算机前提条件和依赖项检查。符合条件的修复可以续订缺失的 DHCP 租约、释放排队的打印作业、重新同步时钟、更新 Defender 签名、恢复符合条件的服务以及修复已确认的 Windows 损坏。已停止的自动启动服务可以在验证其启动窗口和依赖项后启动。当空闲状态是唯一的证据时，已停止的按需启动服务保持不变；只有当前功能证据支持启动时，范围较窄的专用工作流程才可能要求启动它。启动类型、任务定义、报告、转储、订阅、凭据、通道设置、防火墙策略和受管理的设置保持不变。历史、备份和传输快照是只读的。不会打开转储内容。脏位检查不会安排修复或重启。此工作流程不会安装更新、更改驱动程序、删除文件或执行完整的硬件测试。

关键指标

捕获可用内存、提供程序报告的磁盘运行状况和 BitLocker 保护状态，然后将当前指标与设备问题、可靠性历史记录、硬件错误记录、崩溃证据、意外关机和 Windows 内存诊断结果进行关联。重启指示、系统磁盘可用空间、权限提升和更新服务配置仍会显示。不会收集恢复密码。此工作流程不运行任何修复。综合结果并不是完整的硬件、软件或稳定性测试。

可靠性历史记录

读取过去 14 天的 Windows 可靠性监视器记录以及最近的 Application 错误和意外关机事件，然后返回一个有范围限制的历史结论。历史记录不能确定当前运行状况或根本原因。不会选择任何修复，也不会更改任何应用程序、服务或设置。

启动性能

读取过去 14 天的 Windows 启动和关机性能事件元数据，仅保留提供程序标识和有范围限制的数值持续时间字段，然后将其与受支持的待处理重启指示进行关联。在保存证据之前，会删除路径、进程名称、账户和其他事件负载。历史性能下降记录不能识别当前的瓶颈，也不能授权更改启动、服务、应用程序、驱动程序、任务、电源、重启或策略。

硬件错误历史记录

读取过去 14 天的 Windows 硬件错误体系结构和内存诊断历史记录、当前的即插即用设备问题、物理磁盘运行状况以及提供程序的可靠性计数器，然后返回一个有范围限制的硬件结论。这些记录需要与其负载、固件诊断和供应商硬件测试进行关联。不会推断故障组件或根本原因，不会选择任何修复，也不会更改任何硬件、固件、驱动程序、磁盘、池、卷、文件、服务、电源、重启或设置。

驱动程序安装历史记录

读取 Windows SetupAPI 设备安装历史记录中保留的末尾部分，将失败的部分与当前确切的即插即用标识进行关联，并返回一个有范围限制的结论。历史日志部分不能证明设备仍然存在或故障仍在发生。不会安装、删除、回滚或更新任何驱动程序。

系统还原点

列出最多 256 个可用的系统还原点，查看明确的创建条件，并返回一个有范围限制的就绪结论。该列表不能证明每个卷都已启用保护，也不能证明还原会成功。诊断期间不会创建、删除或应用任何还原点。

Windows 恢复环境

Windows 激活

在不收集完整或部分产品密钥的情况下读取当前 Windows 许可证状态，保留过去七天经过清理的软件保护警告、错误和严重事件元数据，然后返回一个有范围限制的运行结论。在保存证据之前，会删除事件负载。当前许可状态报告为 Licensed 时，历史记录仅作为背景信息。不会选择任何激活、产品密钥、令牌、许可证、账户、服务或策略操作。提供程序状态和事件历史不能证明订阅权利、激活服务器可访问性、令牌存储完整性、未来有效性或根本原因。

Windows 服务

应用程序故障

读取最近的 Application 错误和严重事件以及有范围限制的可靠性监视器历史记录，然后返回一个稳定性历史结论。历史记录不能证明当前故障或根本原因，只能引导更有针对性的诊断。不会停止、修复、删除或重新配置任何应用程序。

显示设备

检查图形适配器和显示器报告的设备错误、硬件 ID 和已安装的驱动程序版本。不安装驱动程序、不重置设备、不更改分辨率。不测试图像质量和物理连接。

输入设备

检查键盘、鼠标和 HID 设备的错误以及驱动程序清单。不捕获按键、不重置设备、不更改驱动程序。不测试物理输入操作。

设备问题

在所有设备类别中查找非零的即插即用配置错误代码，然后将存在的设备证据与有范围限制的 SetupAPI 驱动程序安装、设备设置和即插即用历史记录进行关联。仅凭历史记录不能确定当前故障。请在不更改硬件、驱动程序或配置的情况下，查看确切的设备标识和已批准的驱动程序证据。不验证缺失的设备和物理操作。

使用 BitLocker 工具

选择驱动器号和一项 操作，然后按 运行诊断。

  • 检查 读取加密状态、保护状态和保护器标识。这是默认操作，不会更改任何内容。

  • 启用自动解锁 可以让已加密的数据驱动器在 Windows 启动时解锁。Windows 驱动器必须已完全加密且保护已开启。

操作显示被阻止

被阻止的结果表示所请求的操作无法继续。请阅读消息和日志，了解它是在发送之前停止，还是在之前的某个步骤之后停止。不要以为部分完成的操作已经回滚。最常见的前提条件原因如下。

  • 需要管理员访问权限。 关闭 KillerBench，然后通过 以管理员身份运行 重新启动。
  • 重启状态必须已清除。 Windows 有待处理的重启。请重启计算机，然后再次运行该操作。
  • 存在受管理的策略。 该设置由组策略或设备管理拥有。请在那里更改。
  • 证据已变化。 在首次检查和最后复查之间发生了变化。请再次运行工具以读取新状态。

之前的请求需要核对

KillerBench 发现了一个来自中断请求的待处理记录。请再次运行同一操作。它会检查发生了什么，并在不重复请求的情况下报告实际结果。在命令行中，请使用相应的 -recover 命令，例如 killerbench-cli bitlocker-auto-unlock-recover。

检查显示未完成或未知

无法读取证据，通常是因为 KillerBench 未以管理员身份运行，或者某个 Windows 服务不可用。KillerBench 会如实报告这一点，而不会假定计算机正常。

文件保存位置

日志、待处理记录和已保存的证据位于 %LOCALAPPDATA%\KillerBench 下。每个受保护的操作都有自己的文件夹。如果需要保留更改记录，请保留这些文件。
